## 02.1 이 장에서 다루는 것

이 장을 마치면 "이 일은 어디에 올려야 하는가"라는 질문에 스스로 답할 수 있게 됩니다. Claude는 앱, Messages API, Agent SDK, Claude Code, MCP, Managed Agents라는 서로 다른 표면으로 제공되고, 이 여섯은 기능 목록이 아니라 **누가 루프를 돌리는가**로 갈립니다. 그 축을 잡으면 제품이 하나 늘어나도 같은 방식으로 분류할 수 있습니다.

Part I의 첫 장이므로 예제부터 만납니다. 온라인 상점 한빛몰의 고객지원 담당자가 오후 두 시에 이런 문의를 받았다고 합시다. "주문 A-1042가 아직 안 왔어요. 그냥 환불해 주세요." 이 한 문의를 처리하려면 주문을 조회하고, 배송 상태를 확인하고, 환불 규정을 적용하고, 경우에 따라 상담원에게 넘겨야 합니다. 이 장은 이 문의를 여섯 표면에 차례로 올려 보고, 이 책이 어느 표면에서 나머지 이야기를 풀어 갈지 정합니다.

시험에는 "표면"이라는 도메인이 없습니다. 그렇다고 이 장을 건너뛰면 안 됩니다. 시험 시나리오의 모든 지문은 "Agent SDK로 만든 고객지원 에이전트"나 "Claude Code를 쓰는 팀"처럼 표면을 전제로 시작합니다. 전제를 모르면 지문이 설명하는 상황이 머리에 그려지지 않습니다.

## 02.2 하나의 문의, 여섯 개의 답

여섯 표면의 차이는 "모델이 얼마나 똑똑한가"가 아니라 "누가 반복을 돌리는가"입니다. 같은 모델을 쓰더라도, 사람이 대화를 이어 가는지, 내 코드가 요청을 반복하는지, Claude Code가 파일을 고치며 스스로 도는지가 다릅니다.

여기서 말하는 "루프"를 먼저 짚어 두겠습니다. 모델은 한 번 부르면 한 번의 응답만 돌려줍니다. 주문을 조회하려면 모델이 "이 도구를 불러라"라고 말하고, 내 쪽에서 실제로 조회한 뒤, 그 결과를 다시 모델에 넣어야 답이 나옵니다. 이 왕복을 몇 번이고 반복하는 장치가 루프입니다. 루프가 없다면 모델은 무엇을 해야 할지 말할 뿐, 실제로 아무것도 하지 않습니다.

그래서 "누가 루프를 돌리는가"가 표면을 가르는 기준이 됩니다. 사람이 대화로 왕복을 이어 가면 앱이고, 내 코드가 반복문을 돌리면 API이며, SDK나 Claude Code가 자기 루프를 돌리면 나는 결과만 받습니다.

| 표면 | 누가 루프를 돌리는가 | 도구는 어디서 실행되는가 | 상태는 어디에 있는가 |
|---|---|---|---|
| Claude 앱 | 사람과 모델의 대화 | 앱이 제공하는 기능 | 앱의 대화 기록 |
| Messages API | 내 코드 | 내 서버 | 내 저장소(API는 무상태) |
| Agent SDK | SDK가 띄운 에이전트 | 내 프로세스가 가진 내장 도구·MCP | SDK 세션 |
| Claude Code | Claude Code 자체 | 내 터미널·IDE·데스크톱의 파일과 명령 | 프로젝트와 세션 |
| MCP | (해당 없음) 도구를 꽂는 규격 | 서버 프로세스 | 서버가 정함 |
| Managed Agents | Anthropic의 호스팅 런타임 | Anthropic 샌드박스 또는 자체 호스팅 샌드박스 | 관리되는 세션 |

표에서 MCP만 "루프를 돌리는 주체"가 비어 있습니다. 이것이 이 장에서 가장 중요한 구분입니다. MCP는 실행 환경이 아니라 연결 규격입니다. 다음 절에서 따로 설명합니다.

표를 외울 필요는 없습니다. 대신 각 표면에서 "내가 쓰는 코드가 어느 정도인가"를 보십시오. 앱은 0줄, Claude Code는 설정 몇 줄, Agent SDK는 옵션 몇 줄, Messages API는 수십 줄입니다. 코드가 많을수록 통제가 늘고 책임도 늘어납니다. 처음에는 적은 코드로 시작해, 통제가 필요해질 때 내려가는 방식이 안전합니다.

## 02.3 표면을 가르는 네 질문

표면을 고를 때는 네 가지만 물으면 됩니다. 요리를 어디에 맡길지 정하는 것과 비슷합니다. 직접 요리하면 재료와 순서를 다 알지만 시간이 들고, 셰프를 부르면 내 주방에서 내 재료로 요리하되 지시는 내가 하며, 급식 업체에 맡기면 주방까지 그쪽이 씁니다. 이 비유는 "누가 조리하는가"를 보여 주는 데는 맞지만, "누가 재료를 사는가"는 말해 주지 않습니다. 실제 시스템에서는 재료(데이터)의 위치가 결정을 뒤집는 경우가 많습니다.

네 질문은 순서대로 답하지 않아도 됩니다. 다만 하나라도 건너뛰면 나중에 되돌아옵니다. 특히 상태 보관은 처음에 정하지 않으면 4장에서 요청을 만들 때 다시 고민하게 되고, 그때는 이미 코드를 절반쯤 쓴 뒤입니다.

첫째 질문은 **루프를 내가 제어해야 하는가**입니다. 도구 호출 사이에 검증을 넣고, 재시도를 세고, 사람 승인을 걸어야 한다면 루프를 내 손에 두어야 합니다. Messages API와 Agent SDK가 여기 해당합니다.

이 질문은 생각보다 자주 "예"가 됩니다. 한빛몰의 환불처럼 금액이 큰 작업은 실행 전에 승인을 받아야 하고, 그 승인은 모델이 아니라 내 코드가 확인합니다. 모델에게 "승인받았는지 확인해"라고 부탁하는 방식은 승인을 건너뛰는 경로를 남깁니다. 9장에서 이 차이를 프로그램적 강제와 프롬프트 지시로 나눠 다룹니다.

둘째는 **도구가 어디서 실행되어야 하는가**입니다. 사내 DB와 파일 시스템을 건드려야 하고 데이터가 밖으로 나가면 안 된다면, 도구는 내 프로세스나 사내 서버에서 돌아야 합니다.

이 질문에 답하려면 데이터 흐름을 그려야 합니다. 주문 정보가 모델에게 가는 순간, 그 정보는 요청의 일부가 되어 밖으로 나갑니다. 조회 결과를 모델에게 보내지 않고 처리할 수는 없으므로, "데이터가 나가도 되는가"를 먼저 정하고, 안 된다면 마스킹이나 요약을 거쳐야 합니다. 어떤 표면을 고르든 이 결정은 피할 수 없습니다.

셋째는 **상태를 누가 들고 있는가**입니다. Messages API는 무상태입니다. 매 요청에 대화 전체를 실어 보내야 하고, 그 대화를 어디에 저장할지는 내가 정합니다. 반대로 Managed Agents는 세션이 서버에 남습니다.

무상태라는 말은 기억이 없다는 뜻이지, 대화를 이을 수 없다는 뜻이 아닙니다. 대화를 잊지 않게 하려면 내가 이력을 들고 다니면 됩니다. 4장에서 이 방식을 자세히 봅니다. 상태를 내가 들고 있으면 감사와 재현이 쉬워지고, 서버가 들고 있으면 클라이언트 코드가 가벼워집니다.

넷째는 **얼마나 오래 도는가**입니다. 1초 안에 끝나는 문의 응답과, 몇 시간 동안 파일을 고치고 테스트를 돌리는 작업은 다른 표면이 필요합니다.

시간은 비용과도 연결됩니다. 오래 도는 작업은 요청 수가 많아지고, 요청이 많아지면 토큰이 쌓입니다. "짧은 요청이 많다"와 "긴 작업이 적다"는 같은 총량처럼 보여도 최적화 지점이 다릅니다. 앞은 응답당 토큰을 줄이는 일이, 뒤는 중간 결과를 얼마나 남길지 정하는 일이 중요해집니다.

쉽게 말해, 표면 선택은 "이 일의 반복을 누구에게 맡길 것인가"를 정하는 일입니다. 반복을 사람이 맡으면 앱, 내 코드가 맡으면 API, 남이 만든 루프가 맡으면 SDK나 Claude Code입니다.

## 02.4 앱 — 가장 빠르고 가장 닫힌 표면

Claude 앱은 가장 빠른 시작점이고, 동시에 가장 닫힌 표면입니다. 한빛몰 담당자가 오늘 오후에 이 문의를 처리해야 한다면, 앱에 주문 내역을 붙여 넣고 답변 초안을 받는 것으로 충분할 수 있습니다. 코드를 쓰지 않고, 10분이면 끝납니다. 이 장에서 유일하게 코드가 필요 없는 표면입니다.

그러나 앱은 자동화의 표면이 아닙니다. 주문 조회를 앱이 대신 해 주지 않고, 답변을 고객에게 보내는 일도 하지 않습니다. 사람이 복사해 붙여 넣는 순간마다 사람의 시간이 듭니다. 하루 수십 건이면 괜찮지만 하루 수천 건이면 감당이 안 됩니다.

앱을 쓸지 판단하는 기준은 간단합니다. **같은 요청이 하루 몇 번 오는가, 그리고 그 응답에 사람의 판단이 꼭 필요한가.** 하루 열 번이고 판단이 필요하면 앱이 맞습니다. 하루 수백 번이고 규칙으로 처리할 수 있으면 아래의 표면으로 내려가야 합니다.

앱에도 장점이 있습니다. 붙여 넣기만 하면 되므로 개발 비용이 0이고, 결과를 사람이 즉시 검토합니다. 파일 업로드와 이미지 입력도 앱이 가장 간단합니다. 반대로 감사 기록을 남기기 어렵고, 답변 형식을 고정하기 어렵고, 같은 요청을 자동으로 반복할 수 없습니다. 이 세 가지가 필요해지는 순간이 앱을 떠날 때입니다. 코드가 필요 없다는 점도 장점이지만, 코드가 없다는 것은 자동화가 없다는 뜻이기도 합니다.

## 02.5 Messages API — 내 코드가 루프를 돌린다

Messages API는 모델을 부품으로 쓰는 가장 낮은 단계입니다. 요청 하나를 보내면 응답 하나가 오고, 그다음에 무슨 일을 할지는 전적으로 내 코드가 정합니다. 루프, 도구 실행, 재시도, 저장이 모두 내 몫입니다.

이 블록이 하는 일은 주문 문의 하나를 모델에 보내는 최소 요청을 보여 주는 것입니다. 필드는 네 개뿐이고, 나머지는 나중에 붙습니다.

```json
{
  "model": "claude-sonnet-5-5",
  "max_tokens": 1024,
  "system": "너는 한빛몰 고객지원 에이전트다. 확인하지 않은 사실을 추측하지 않는다.",
  "messages": [
    {"role": "user", "content": "주문 A-1042가 아직 안 왔어요. 그냥 환불해 주세요."}
  ]
}
```

여기서 확인할 것: `system`은 대화가 아니라 지시이고, `messages`는 사용자와 어시스턴트의 주고받음만 담습니다. `max_tokens`는 응답 길이의 상한이며, 이 값에 걸리면 응답이 잘립니다.

응답은 다음과 같은 모양으로 옵니다. 본문 외에 `stop_reason`과 `usage`가 함께 오는 점을 눈여겨보십시오. 이 두 필드가 4장과 5장의 주인공입니다.

```json
{
  "id": "msg_01XFDUDYJgAACzvnptvVoYEL",
  "type": "message",
  "role": "assistant",
  "content": [{"type": "text", "text": "주문 번호를 확인했습니다. 배송 상태를 먼저 확인하겠습니다."}],
  "model": "claude-sonnet-5-5",
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "usage": {"input_tokens": 312, "output_tokens": 41}
}
```

여기서 확인할 것: `content`는 블록의 목록입니다. 지금은 텍스트 블록 하나지만, 도구를 쓰면 `tool_use` 블록이 섞여 옵니다. 응답을 문자열로 다루면 이 구조를 잃습니다.

Messages API의 장점은 통제권입니다. 도구를 실행하기 전에 검증을 넣고, 실패하면 재시도 횟수를 세고, 응답을 DB에 저장하고, 비용을 호출 단위로 기록할 수 있습니다. 단점은 그 통제권이 전부 내 책임이라는 점입니다. 루프를 잘못 짜면 무한 반복이 되고, 도구 오류를 처리하지 않으면 대화가 멈춥니다. 5장에서 이 책임을 직접 집니다.

요청에는 버전도 함께 실립니다. 2026-11-24 기준 문서의 예시는 `anthropic-version: 2026-10-21` 헤더를 씁니다. 버전을 생략하면 서버의 기본 동작에 기대게 되고, 그 동작은 바뀔 수 있습니다. 재현 가능한 시스템을 만들려면 버전을 명시하는 편이 안전합니다. 이 책의 코드도 버전을 고정해 두었습니다.

무상태라는 점은 요금에도 영향을 줍니다. 대화가 길어지면 매번 이전 대화를 다시 보내야 하므로 입력 토큰이 늘어납니다. 세 번째 요청은 첫 번째 요청보다 훨씬 큰 입력을 갖습니다. 이 비용 구조를 알면 "대화를 얼마나 길게 가져갈 것인가"가 설계 결정이 됩니다. 27장의 컨텍스트 관리와 35장의 캐싱이 모두 여기서 시작합니다.

## 02.6 Agent SDK — Claude Code의 루프를 라이브러리로

Agent SDK는 Claude Code를 라이브러리로 쓰는 표면입니다. 파일 읽기, 명령 실행, 검색 같은 내장 도구와 권한, 세션, 훅을 그대로 가져오면서 내 파이썬·타입스크립트 프로그램 안에서 돌립니다. 루프를 내가 짜지 않아도 되고, 대신 SDK가 정한 방식대로 돕니다.

이 블록이 하는 일은 SDK에 "이 작업을 이 도구들만 써서, 최대 몇 단계까지" 지시하는 옵션을 만드는 것입니다.

```python
from claude_agent_sdk import ClaudeAgentOptions, query

options = ClaudeAgentOptions(
    model="claude-sonnet-5-5",
    system_prompt="너는 한빛몰 고객지원 에이전트다. 주문은 도구로 확인한다.",
    allowed_tools=["Read", "Grep", "mcp__hanbit__lookup_order"],
    max_turns=8,
    effort="medium",
)

async for message in query(prompt="주문 A-1042 상태를 확인해 줘", options=options):
    print(message)
```

여기서 확인할 것: `allowed_tools`가 권한의 전부입니다. 여기 없는 도구는 모델이 불러도 실행되지 않습니다. `max_turns`는 루프의 상한이고, `effort`는 3장에서 다룰 손잡이입니다.

이 코드의 필드 이름과 `query`의 시그니처는 2026-11-24에 `claude-agent-sdk` 0.2.187에서 확인했습니다. 다만 실제 에이전트 실행은 이 환경에 Claude Code 실행 파일과 API 키가 없어 돌리지 못했습니다. 옵션 구성이 받아들여지는지까지가 검증 범위입니다.

Agent SDK를 고르는 기준은 "내 앱 안에서 코드를 다루는 에이전트가 필요한가"입니다. 저장소를 읽고 고치는 작업, 사내 파일을 뒤지는 작업, 여러 단계를 스스로 밟는 작업에 맞습니다. 반대로 고객 응대처럼 응답 하나하나를 통제해야 하는 일에는 Messages API가 더 맞습니다. SDK는 편한 만큼 루프의 세부를 감춥니다.

감춰지는 것을 알면 디버깅이 쉬워집니다. SDK는 내부적으로 Claude Code 실행 파일을 띄워 대화를 주고받습니다. 그래서 설치 형태에 따라 실행 파일이 함께 오기도 하고, 없으면 따로 설치해야 합니다. 에러 메시지에 실행 파일 경로가 나오면 이 구조를 떠올리십시오. "파이썬 라이브러리를 불렀는데 왜 실행 파일이 필요하지"라는 의문이 여기서 풀립니다.

권한 설정도 SDK의 일부입니다. 도구를 전부 열어 두면 편하지만 위험합니다. 이 예처럼 필요한 도구만 나열하면, 모델이 목록 밖의 도구를 부르더라도 실행되지 않습니다. 32장에서 같은 원칙을 MCP 서버에 적용합니다.

SDK를 배우면 Claude Code 문서를 함께 읽게 되는 이유도 여기 있습니다. 둘은 같은 루프를 공유합니다. Claude Code에서 되는 것이 SDK에서 대개 되고, SKILL.md나 훅처럼 파일로 설정하는 것은 그대로 읽힙니다. 4부를 먼저 읽고 이 장으로 돌아오는 것도 좋은 순서입니다.

## 02.7 Claude Code — 작업장이라는 표면

Claude Code는 터미널, IDE 확장, 데스크톱 앱, 브라우저에서 동작하는 에이전틱 코딩 도구입니다. 코드베이스를 읽고, 파일을 고치고, 명령을 실행합니다. 이 책의 4부가 이 표면을 다룹니다.

표면으로서 Claude Code의 특징은 **작업장이 딸려 온다**는 점입니다. 모델만 있는 것이 아니라, 프로젝트 규칙 파일, 스킬, 서브에이전트, 훅, 권한 설정이 함께 있습니다. 그래서 "같은 결과를 매번 같은 방식으로" 만들기가 다른 표면보다 쉽습니다. 17장의 CLAUDE.md, 18장의 스킬, 21장의 CI 연동이 모두 이 작업장을 세우는 일입니다.

작업장이 딸려 온다는 말은, 잘못 세우면 그 잘못이 모든 작업에 복제된다는 뜻이기도 합니다. 규칙 파일에 오래된 내용을 남겨 두면 매번 그 규칙을 따릅니다. 그래서 4부는 기능 소개보다 "무엇을 어디에 적을 것인가"에 시간을 더 씁니다.

한빛몰 예로 돌아오면, Claude Code는 고객 응대에 쓰기보다 **그 응대 시스템을 만드는 데** 씁니다. 지원 에이전트의 코드를 짜고, 테스트를 만들고, 배포 스크립트를 고치는 작업이 여기에 해당합니다. 32장의 MCP 서버도 Claude Code로 만들고 Claude Code에 붙입니다.

네 가지 실행 형태가 있다는 점도 기억하십시오. 터미널, IDE 확장, 데스크톱 앱, 브라우저입니다. 기능은 거의 같지만 쓰는 자리가 다릅니다. 코드 옆에서 고치고 싶으면 IDE, 원격 서버에 붙고 싶으면 터미널, 브라우저만 있는 환경이면 웹을 씁니다. 4부에서 이 차이를 다룹니다.

## 02.8 MCP — 표면이 아니라 콘센트

MCP(Model Context Protocol)를 여섯 번째 표면으로 부르는 경우가 많은데, 정확히는 표면이 아닙니다. MCP는 도구와 데이터를 꽂는 규격입니다. 2026-07-28 명세는 호스트, 클라이언트, 서버의 세 역할을 정의하고, 서버가 제공할 수 있는 것을 도구(tools), 리소스(resources), 프롬프트(prompts)로 나눕니다.

벽의 콘센트와 비슷합니다. 콘센트 자체는 전기를 만들지 않지만, 규격이 같으면 어떤 기계든 꽂아 쓸 수 있습니다. 이 비유가 맞는 지점은 "한 번 만들면 여러 곳에 꽂힌다"는 것입니다. 깨지는 지점은 안전입니다. 콘센트는 규격만 맞으면 그냥 꽂히지만, MCP 서버는 클라이언트가 도구 목록을 받아 사용자에게 보여 주고 승인을 받는 절차를 거칩니다.

MCP가 표면이 아니라는 사실은 실무에서 중요합니다. "MCP로 에이전트를 만든다"는 말은 성립하지 않습니다. MCP 서버를 만들고, 그 서버를 Messages API·Agent SDK·Claude Code 중 하나에 꽂아야 에이전트가 돕니다. 15장에서 소비자 입장의 설정을, 32장에서 생산자 입장의 구현을 다룹니다.

규격이 나뉘는 방식도 알아 두십시오. 호스트는 사용자가 쓰는 프로그램(Claude Code, 데스크톱 앱 등)이고, 클라이언트는 호스트 안에서 서버 하나와 연결을 맡는 부분이며, 서버는 도구와 데이터를 제공합니다. 한 호스트가 여러 서버를 동시에 붙일 수 있고, 같은 서버를 여러 호스트가 쓸 수 있습니다. 이 구조 덕분에 도구를 한 번 만들어 여러 곳에서 재사용합니다.

보안 책임도 이 구조에서 갈립니다. 서버는 자기가 가진 데이터의 권한을 지고, 호스트는 어떤 서버를 붙일지와 어떤 도구를 허용할지를 정합니다. 명세는 도구 설명을 신뢰하지 말라고 권고합니다. 서버가 제공하는 설명은 데이터와 함께 움직이므로, 남이 만든 서버의 설명을 그대로 사용자에게 보여 주면 안 됩니다. 15장과 35장에서 이 주제를 다시 다룹니다.

MCP의 세 가지 제공물도 구분해야 합니다. 도구는 모델이 호출하는 동작이고, 리소스는 클라이언트가 읽는 데이터이며, 프롬프트는 사용자가 고르는 문장 틀입니다. 32장에서 카탈로그를 도구가 아니라 리소스로 둔 이유가 여기 있습니다. 읽기만 하는 데이터를 도구로 만들면 모델이 확인할 때마다 호출이 쌓입니다.

쉽게 말해, MCP는 "도구를 꽂는 규격"이고, 에이전트를 돌리는 것은 그 도구를 꽂은 표면입니다. 둘을 섞으면 "왜 MCP를 만들었는데 아무것도 안 돌지"라는 질문이 나옵니다.

## 02.9 Managed Agents — 루프를 맡기는 선택

Managed Agents는 Anthropic이 에이전트 하네스와 실행 환경을 호스팅하는 표면입니다. 2026년에 추가된 표면이고, 2026년 11월 현재 베타입니다. 모든 요청에 `managed-agents-2026-04-01` 베타 헤더가 필요하고, SDK를 쓰면 자동으로 붙습니다.

개념은 넷입니다. 에이전트(모델·시스템 프롬프트·도구·MCP 서버·스킬의 묶음), 환경(세션이 도는 곳, Anthropic 관리 샌드박스 또는 자체 호스팅), 세션(특정 작업을 수행하는 실행 단위), 이벤트(애플리케이션과 에이전트가 주고받는 메시지)입니다. 장시간 실행, 상태 유지, 스케줄 실행이 필요할 때 맞습니다.

주의할 점이 있습니다. Managed Agents는 설계상 상태를 보관하므로 **Zero Data Retention과 HIPAA BAA 대상이 아닙니다.** 자체 호스팅을 쓰면 데이터를 직접 보관하는 예외가 적용됩니다. 규제 산업에서 쓰려면 이 조항을 먼저 확인해야 합니다. 규정을 모르고 도입하면 나중에 되돌리는 비용이 큽니다.

Messages API와 무엇이 다른지 한 줄로 비교하면 이렇습니다. Messages API는 모델 호출만 주고, 루프·도구 실행·환경은 내 몫입니다. Managed Agents는 그 셋을 미리 만들어 두고 빌려 줍니다. 그래서 커스텀 루프와 세밀한 제어가 필요하면 Messages API, 장시간·반복 실행과 인프라 최소화가 목표라면 Managed Agents입니다.

쓰는 방식도 다릅니다. 에이전트를 한 번 정의해 두고 세션을 열어 이벤트를 보내면, Claude가 도구를 스스로 돌리며 결과를 스트리밍합니다. 중간에 추가 이벤트를 보내 방향을 돌리거나 중단할 수도 있습니다. 이벤트 이력은 서비스가 보관하고 전체를 받아 볼 수 있습니다.

베타라는 표시를 가볍게 넘기지 마십시오. 베타는 기능이 빠질 수 있다는 뜻이 아니라, 동작이 릴리스 사이에 다듬어질 수 있다는 뜻입니다. 운영 시스템에 넣을 때는 버전 헤더를 고정하고, 바뀜을 감지할 테스트를 두십시오. 헤더 없이 호출하면 어느 날 조용히 다른 동작을 만나게 됩니다.

## 02.10 한빛몰의 선택

이제 한빛몰의 문의로 돌아옵니다. 하루 800건의 문의를 처리해야 하고, 주문·고객 정보는 사내 ERP에 있으며, 환불은 규정에 따라 자동 처리하되 일정 금액을 넘으면 상담원 승인이 필요합니다. 이 조건을 네 질문에 넣으면 답이 좁혀집니다.

| 결정 | 선택 | 이유 |
|---|---|---|
| 루프의 주인 | 내 코드(Messages API) | 환불 금액에 따라 승인을 끼워 넣어야 함 |
| 도구 실행 위치 | 사내 서버 | 주문·고객 데이터가 사내에만 있음 |
| 상태 보관 | 내 DB | 대화 기록을 상담 이력과 함께 남겨야 함 |
| 실행 시간 | 초 단위 | 문의 응답이 목적이고 장기 작업이 아님 |

그래서 이 책의 2부는 Messages API로 루프를 짜는 길을 갑니다. Agent SDK는 7부에서 사내 도구를 만들 때, Claude Code는 코드 작업을 할 때, Managed Agents는 35장에서 선택 기준을 비교할 때 다시 나옵니다. MCP는 15장과 32장에서 도구를 꽂는 규격으로 등장합니다.

이 선택은 독자의 회사에서도 그대로 맞지는 않을 것입니다. 그래서 표를 외우라고 하지 않았습니다. 네 질문에 답하는 연습을 했으니, 다음 프로젝트에서 표면을 다시 골라야 할 때 같은 절차를 반복하십시오. 한 시간이면 끝나는 일입니다.

선택이 항상 이렇게 깔끔하지는 않습니다. 문의 응답과 코드 수정이 한 서비스에 섞여 있으면 표면도 섞입니다. 그때는 "이 요청은 누가 끝까지 책임지는가"를 기준으로 나누십시오. 한 요청 안에서 표면을 두 개 섞으면 실패했을 때 어느 쪽을 고쳐야 할지 알기 어려워집니다.

섞어야 한다면 경계를 문서로 남기십시오. "문의 응답은 A 서비스가, 코드 수정은 B 에이전트가 맡고, 두 사이는 큐로 전달한다"처럼 적어 두면, 장애가 났을 때 어느 쪽 로그를 볼지 정해집니다. 표면 선택은 아키텍처 문서의 한 줄이지만, 그 한 줄이 운영 단계에서 시간을 크게 줄입니다.

비용도 표면에 따라 다릅니다. 같은 문의를 처리해도 앱은 사람 시간을 쓰고, API는 토큰을 쓰고, Managed Agents는 토큰과 샌드박스 자원을 씁니다. 3장에서 토큰 단가를 계산하는 법을 배우면, 표면 선택을 비용으로 비교할 수 있게 됩니다.

## 02.11 실습 — 같은 문의를 여섯 표면에 올려 보기

이 실습은 코드를 쓰지 않습니다. 표면 선택을 몸에 익히는 것이 목적이고, 20분이면 끝납니다.

1. 방금 읽은 한빛몰 문의를 종이에 적습니다. 조건은 하루 800건, 사내 ERP, 환불 승인 규칙입니다.
2. 여섯 표면을 한 줄씩 적고, 각 표면에 "이 표면으로 처리하면 무엇이 좋고 무엇이 불가능한가"를 적습니다.
확인: Managed Agents를 고르면 "Zero Data Retention 미적용"이라는 조건이 걸리는지 스스로 짚을 수 있어야 합니다.
3. 네 질문(루프의 주인, 도구 위치, 상태 보관, 실행 시간)에 답을 적습니다.
확인: 네 답 중 하나라도 "모르겠다"이면 그 항목이 현업에서 확인해야 할 질문입니다.
4. 우리 회사의 실제 문의 하나를 같은 방식으로 적어 봅니다.
확인: 실제 업무에서는 표면이 하나로 정해지지 않고, "조회는 API, 코드 수정은 Claude Code"처럼 나뉘는 경우가 많다는 것을 발견합니다.

실습을 마쳤으면 표를 한 장 더 만들어 보십시오. 우리 팀이 지금 쓰는 표면과, 6개월 뒤에 쓸 표면을 나란히 적습니다. 대개 지금은 앱, 6개월 뒤는 API나 Claude Code가 됩니다. 이 변화를 미리 그려 두면 다음 프로젝트에서 같은 논의를 반복하지 않습니다.

## 02.12 이 개념이 프로덕션에서 커지는 지점

표면 선택은 한 번 정하고 끝나지 않습니다. 처음에는 Messages API로 시작해도, 코드 수정 업무가 붙으면 Claude Code를 옆에 두게 되고, 사내 시스템 여럿을 연결하면 MCP 서버를 만들게 됩니다. 32장의 `docs-hub`가 그 예입니다. 같은 도구 목록을 Claude Code와 Agent SDK가 함께 쓰도록 만드는 일이 7부의 주제입니다.

이 장의 결론은 "어느 표면이 좋은가"가 아니라 "어느 표면이 이 일의 책임을 질 수 있는가"입니다. 이 질문을 습관으로 만들면 제품이 새로 나올 때도 당황하지 않습니다. 새 표면이 나오면 "누가 루프를 돌리고, 도구는 어디서 돌고, 상태는 어디에 남는가"만 물으면 됩니다.

- [ ] 여섯 표면을 "누가 루프를 돌리는가"로 구분해 설명할 수 있다.
- [ ] MCP가 실행 표면이 아니라 연결 규격임을 안다.
- [ ] 표면을 고르는 네 질문을 우리 업무에 적용해 봤다.
- [ ] Messages API가 무상태이며 대화 이력은 내가 보관한다는 것을 안다.
- [ ] Agent SDK가 Claude Code의 루프를 라이브러리로 쓰는 표면임을 안다.
- [ ] Claude Code가 터미널·IDE·데스크톱·브라우저에서 동작함을 안다.
- [ ] Managed Agents가 베타이고 ZDR·HIPAA 대상이 아님을 안다.
- [ ] 한빛몰 예에서 왜 Messages API를 골랐는지 설명할 수 있다.

다음 장에서는 표면 위에 올릴 모델을 고릅니다. 같은 루프라도 모델과 손잡이에 따라 비용이 몇 배 차이 나고, 그 차이를 계산하지 못하면 프로젝트가 예산에서 먼저 멈춥니다.
