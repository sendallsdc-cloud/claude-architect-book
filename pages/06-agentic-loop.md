## 06.1 이 장에서 다루는 것

이 장을 마치면 5장의 루프가 **끝나는 방식 네 가지**를 더 구분하게 됩니다. 서버 도구가 잠시 멈춘 `pause_turn`, 모델이 답을 거절한 `refusal`, 텍스트 없이 끝난 `end_turn`, 창을 넘겨 잘린 응답입니다. 그리고 어느 단계에서 멈췄는지 디스크에 남겨, 다음 실행이 그 자리에서 이어 달리게 만듭니다.

5장의 루프는 `stop_reason`을 읽고 분기했습니다. `end_turn`이면 답을 반환하고, `tool_use`면 도구를 실행하고, `max_tokens`면 예외를 던졌습니다. 그 셋만으로도 정상 경로는 잘 돌았습니다. 이 장은 나머지 네 값을 다룹니다. 운영에서 사고는 대개 정상 경로가 아니라 여기서 납니다.

이 장의 결과물은 `work/ch06-lifecycle/loop_v2.py`입니다. 5장 폴더의 `schemas.py`와 `tools.py`를 그대로 불러 쓰고, 호출부는 `transport.py`를 그대로 씁니다. 바뀐 것은 루프 본체와 대본 네 개입니다. 코드는 실행해 확인했고, 검증 로그를 06.3부터 06.6까지의 절에 실었습니다.

이 장을 읽고 나면 루프를 "반복문"이 아니라 **상태 기계**로 보게 됩니다. 상태 기계란 지금 어느 상태에 있고, 어떤 신호가 오면 어디로 가는지를 표로 그릴 수 있는 구조입니다. 5장의 루프는 상태가 셋이었습니다. 이 장은 일곱으로 늘립니다. 상태가 늘어도 루프의 길이는 크게 늘지 않습니다. 분기마다 하는 일이 짧기 때문입니다. 길어지는 것은 오히려 로그와 예외의 종류입니다. 그 둘이 늘어나는 것을 두려워하지 마십시오. 운영에서 루프를 고칠 때 필요한 것은 그 둘입니다. 예외의 이름을 모르면 장애 보고서를 쓸 수 없고, 로그가 없으면 "왜 여기서 멈췄는가"에 답할 수 없습니다.

이 장의 분기 일곱은 모두 4장의 표에서 왔습니다. 새로 나오는 값은 없습니다. 4장에서 이름만 보고 지나간 값들을 이제 코드로 옮기는 것입니다. 그래서 이 장을 읽을 때 4장의 표를 옆에 펼쳐 두면 좋습니다. 표의 "다음 행동" 열이 이 장의 각 분기가 됩니다.

## 06.2 멈춤과 끝남은 다르다

루프를 오래 굴리다 보면 마주치는 첫 번째 오해는 "모델이 말을 멈추면 끝난 것"이라는 생각입니다. 세탁기로 비유하면 분명해집니다. 세탁기는 탈수까지 끝나면 알림을 울리고, 문이 잠긴 채로 잠시 멈추기도 합니다. 둘 다 소리가 나지 않지만 하나는 꺼내야 하고 하나는 기다려야 합니다. 루프도 같습니다. `end_turn`은 꺼내는 신호이고, `pause_turn`은 기다리는 신호입니다. 이 비유가 맞는 곳은 "조용함이 끝을 뜻하지 않는다"는 점입니다. 깨지는 곳은 횟수입니다. 세탁기는 알아서 마치지만, `pause_turn`은 우리가 이어 보내지 않으면 영원히 멈춰 있습니다.

4장에서 `stop_reason` 일곱 값을 표로 보았습니다. 그중 5장이 다룬 것은 셋입니다. 남은 넷은 표의 아래쪽에 있었고, "드물지만 만나면 루프가 엉뚱하게 돈다"고 적어 두었습니다. 이 장이 그 넷을 실제 분기로 만듭니다.

왜 이 값들이 생겼는지도 알아 둘 만합니다. `pause_turn`은 모델이 아니라 **서버 쪽 도구**가 오래 걸릴 때 나옵니다. 서버 도구는 우리 코드가 아니라 Anthropic 쪽에서 실행되므로, 한 번의 응답 안에서 반복 횟수를 다 쓰면 "여기까지 했으니 이어서 시키십시오"라는 뜻으로 멈춥니다. `refusal`은 안전 분류기가 요청을 거절한 경우입니다. 2026년 모델들은 이런 분류기를 갖고 있고, 거절은 오류가 아니라 **정상 응답**으로 돌아옵니다.

두 값의 공통점은 이것입니다. **요청은 성공했고, 모델은 일을 마치지 않았습니다.** 그래서 HTTP 오류로 처리하면 안 되고, 예외로 던져 루프를 죽여도 안 됩니다. 루프가 알아야 할 것은 "지금 무엇을 다시 보내야 하는가"입니다.

이 구분은 비용에도 영향을 줍니다. HTTP 오류는 대개 재시도하면 같은 오류가 오지만, `pause_turn`은 다시 보내면 진행됩니다. 반대로 `refusal`은 다시 보내도 같은 결정이므로 같은 요청을 반복하면 요금만 두 번 나갑니다. 세 경우를 한 덩어리로 "실패"라고 부르면, 재시도 정책을 하나로 정할 수밖에 없고, 그 하나는 셋 중 둘에게 틀립니다. 그래서 이 장은 예외의 이름을 나눕니다.

고르는 절차를 하나 더하면 이렇습니다. 먼저 "이 멈춤이 우리 코드 밖에서 생겼는가"를 묻습니다. 밖에서 생겼으면 `pause_turn`이나 거절이고, 안에서 생겼으면 빈 응답이나 잘림입니다. 그다음 "같은 요청을 다시 보내면 나아지는가"를 묻습니다. 나아지면 재시도하고, 안 나아지면 입력이나 모델을 바꿉니다. 두 질문만으로 네 경우가 갈립니다. 이 두 질문은 장애 대응 절차서에 그대로 쓸 수 있습니다.

Agent SDK를 쓰면 이 판단을 라이브러리가 대신합니다. 대신 상한을 우리가 정합니다. SDK 문서는 `max_turns`로 턴 수를 제한하고, 상한에 닿으면 최종 답 없이 `error_max_turns` 결과가 온다고 안내합니다. 상한에 닿는 일 자체가 정상이 아니라는 신호라는 점은 5장의 단계 상한과 같습니다.

## 06.3 pause_turn — 받은 내용을 그대로 돌려보낸다

`pause_turn`의 처방은 한 줄입니다. **받은 assistant 내용을 이력에 넣고, 사용자 메시지를 더하지 않은 채 다시 요청합니다.** 새 질문을 붙이면 "이어서 하라"는 뜻이 흐려지고, 내용을 버리면 서버가 어디까지 했는지 알 수 없습니다.

이 상황을 한 번 상상해 보십시오. 고객이 "지난달 주문 세 건 중에 반품한 것까지 합쳐서 정산해 주세요"라고 합니다. 모델은 세 건을 조회하고, 반품 내역을 확인하고, 합계를 계산합니다. 서버 도구가 이 과정을 한 응답 안에서 처리하다가 반복 한도에 닿으면, 모델은 지금까지의 결과를 담은 채 `pause_turn`으로 멈춥니다. 이때 우리가 새 질문을 붙이면 모델은 "추가 요청이 왔다"고 읽고 처음부터 다시 계획할 수 있습니다. 반면 내용을 그대로 돌려보내면 "하던 일의 나머지를 하라"고 읽습니다.

이 블록이 하는 일은 `pause_turn`을 만났을 때 응답을 그대로 이력에 붙이고 다시 도는 분기입니다. 횟수 상한을 함께 둡니다.

```python
if stop == "pause_turn":
    log["pauses"] += 1
    if log["pauses"] > max_pauses:
        raise StepLimit("pause_turn이 상한을 넘었다. 서버 도구 루프가 끝나지 않는다.")
    messages.append({"role": "assistant", "content": response["content"]})
    continue
```

여기서 확인할 것: 새 user 메시지가 없다는 점입니다. 이력의 마지막이 assistant로 끝나고, 그다음 요청이 그대로 이어집니다.

대본으로 돌린 결과입니다. 첫 응답이 `pause_turn`이고, 두 번째 요청에 assistant 블록이 그대로 들어 있습니다.

```text
pause 횟수: 1 / 단계: 3
2번째 요청 메시지 수: 2 / 역할: ['user', 'assistant']
2번째 요청에 assistant 내용이 그대로: True
답변: 김하늘 고객님은 일반 등급이고, 환불은 정책상 가능합니다. 접수할까요?
```

여기서 확인할 것: 두 번째 요청의 메시지가 두 개뿐입니다. 첫 user와, 이어 달라는 assistant입니다. 도구 결과가 끼어들 자리가 없습니다.

상한이 필요한 이유는 간단합니다. 서버 도구가 계속 같은 자리에서 멈추면 우리 루프는 같은 요청을 무한히 보냅니다. 이 장의 예제는 세 번으로 잡았습니다. 세 번을 넘으면 정상이 아니므로 예외로 올리고, 호출부가 사람에게 알립니다.

로그에는 남길 것이 셋입니다. 몇 번째 `pause_turn`이었는지, 그때까지 몇 단계를 지났는지, 마지막 응답에 어떤 도구가 불렸는지입니다. 이 셋이 있으면 "서버 도구가 오래 걸린 것"과 "우리 도구가 계속 같은 자리에서 도는 것"을 나눠 볼 수 있습니다. 전자는 기다리면 되고, 후자는 도구 설명이나 인자를 고쳐야 합니다.

쉽게 말해, `pause_turn`은 "여기까지 했으니 이어서 하라"는 신호입니다. 내용을 그대로 돌려보내면 되고, 새 질문을 붙이면 안 됩니다.

## 06.4 refusal — 거절은 오류가 아니다

`refusal`은 HTTP 200으로 옵니다. 요청이 잘못된 것이 아니라, 모델이 정책상 답하지 않기로 한 것입니다. 응답에는 `stop_details`가 붙고, 그 안에 `category`와 `explanation`이 들어 있습니다. 분류는 사이버, 생물, 경쟁 모델 개발, 추론 추출, 그 밖의 정책 영역 다섯 가지입니다.

처음 만나면 두 가지를 잘못합니다. 첫째, 같은 모델로 다시 묻습니다. 모델은 이미 결정을 내렸으므로 결과가 같고, 요금만 나갑니다. 둘째, 부분 출력을 그대로 씁니다. 거절은 출력 도중에 올 수도 있는데, 그 앞의 문장은 완성된 답이 아닙니다. 부분 출력은 버리는 편이 안전합니다.

처방은 두 갈래입니다. **서버 측 대체**는 요청에 `fallbacks`를 `"default"`로 넣으면 API가 권장 모델로 다시 시도합니다. 2026년 11월 기준 베타이고, Haiku 5.5에는 이 기능이 없습니다. **클라이언트 측 대체**는 우리가 모델 이름을 바꿔 한 번 더 보내는 방식입니다. 이 장의 코드는 두 번째를 씁니다. 흐름이 코드에 보이는 편이 배우기 좋고, 어느 모델로 갔는지 로그에 남기기 때문입니다.

이 블록이 하는 일은 거절을 만났을 때 대체 모델로 한 번만 다시 보내는 분기입니다.

```python
if stop == "refusal":
    details = response.get("stop_details") or {}
    log["refusals"].append(details.get("category"))
    if log["model"] == FALLBACK_MODEL:
        raise Refused(f"대체 모델도 거절했다: {details.get('category')}")
    log["model"] = FALLBACK_MODEL
    continue  # 같은 messages로 대체 모델에 다시 보낸다
```

여기서 확인할 것: `messages`를 건드리지 않습니다. 같은 요청을 다른 모델에 보내는 것이 핵심입니다. 대체 모델도 거절하면 그때는 사람에게 넘깁니다.

```text
거절 분류: ['general_harms'] / 대체: 1
1차 요청 모델: claude-sonnet-5-5 / 2차 요청 모델: claude-opus-5-5
답변: 상담원에게 넘겼습니다. 접수 번호는 CS-2041입니다.
```

여기서 확인할 것: 두 번째 요청의 모델 이름만 달라졌습니다. 대본이지만 요청 본문은 실제와 같은 모양이므로, 모델 전환이 코드에서 일어난다는 것을 확인할 수 있습니다.

`explanation`은 사람에게 보여 주는 문장이고, 문구가 고정되어 있지 않습니다. 화면에 그대로 띄우되, 문장을 파싱해 분기하지 마십시오. 분기에 쓰는 값은 `category`입니다.

고객지원 시스템에서 거절을 만나는 경우는 흔치 않지만, 만나면 대응이 중요합니다. 고객에게 "시스템이 거절했습니다"라고 말하면 안 됩니다. 거절은 우리 쪽 요청 문장에서 온 경우가 많으므로, 상담원이 그 문장을 보고 다시 써야 합니다. 그래서 이 장의 코드는 거절을 상담원 이관으로 끝냅니다. 대체 모델이 답을 주면 그 답을 쓰고, 주지 못하면 사람에게 넘깁니다.

거절을 줄이는 방법은 요청을 바꾸는 것입니다. 같은 뜻을 다른 말로 쓰는 것이 아니라, 목적을 분명히 적는 것입니다. "이 주문을 다른 이름으로 다시 만들어 주세요"는 무엇을 원하는지 알 수 없어 정책에 닿기 쉽습니다. "배송지를 잘못 입력해 주문을 다시 만들어야 한다. 기존 주문을 취소하고 같은 상품으로 재주문하는 절차를 안내해 달라"는 목적과 수단이 드러납니다. 거절은 대개 모델의 문제가 아니라 요청의 모호함에서 옵니다.

대체 모델로 다시 보내면 입력 토큰을 두 번 지불합니다. 프롬프트가 길면 이 비용이 만만치 않습니다. 이를 줄이기 위한 크레딧 제도가 따로 있고, 서버 측 대체를 쓰면 그 계산이 API 쪽에서 처리됩니다. 지금 단계에서는 "거절 한 번에 요금이 두 번 나갈 수 있다" 정도만 기억하면 충분합니다.

## 06.5 빈 end_turn — 조용한 실패

가장 찾기 어려운 것은 `end_turn`인데 내용이 빈 응답입니다. 오류도 아니고, 잘린 것도 아니고, 그냥 아무 말도 없습니다. 5장의 루프는 이때 예외를 던졌습니다. 그 판단은 여전히 맞지만, 원인을 알면 한 번은 더 시도할 수 있습니다.

원인은 대개 둘입니다. 첫째, 도구 결과 뒤에 텍스트를 덧붙인 경우입니다. 이력이 "도구 결과 다음에 사용자 말"이라는 패턴을 보이면 모델은 그 패턴을 따라 턴을 끝냅니다. 둘째, 이미 완료된 응답을 아무것도 더하지 않고 그대로 다시 보낸 경우입니다. 모델은 이미 끝났다고 판단했으므로 계속 끝난 상태로 답합니다.

그래서 처방도 둘입니다. 도구 결과 뒤에 텍스트를 붙이지 마십시오. 그리고 빈 응답은 **되돌려 보내지 말고**, 새 user 메시지로 이어 달라고 요청하십시오. 이 장의 코드는 그 문장을 상수로 두고 한 번만 씁니다.

첫 번째 처방이 왜 필요한지 조금 더 보겠습니다. 우리는 도구 결과를 보낼 때 "결과입니다" 같은 안내를 덧붙이고 싶어집니다. 사람에게 보내는 메시지처럼 느껴지기 때문입니다. 그러나 모델에게 그 메시지는 새 지시로 읽힐 수 있습니다. 특히 결과 뒤에 붙은 문장이 짧으면 "이 턴은 여기서 끝"이라는 신호로 작동합니다. 그래서 도구 결과는 결과만 담고, 안내는 system 프롬프트에 적으십시오.

이 블록이 하는 일은 빈 `end_turn`을 한 번은 이어 달라고 요청하고, 두 번째는 예외로 올리는 분기입니다.

```python
if stop == "end_turn":
    text = text_of(response["content"])
    if text:
        return {"text": text, "messages": messages, "log": log}
    log["continuations"] += 1
    if log["continuations"] > 1:
        raise LoopError("빈 end_turn이 두 번 연속 왔다. 대화 이력의 구조를 확인한다.")
    messages.append({"role": "user", "content": CONTINUATION})
    continue
```

여기서 확인할 것: 빈 응답을 이력에 넣지 않습니다. 넣으면 "끝난 턴"이 이력에 박히고, 그다음 요청도 같은 상태에서 시작합니다.

```text
연속 요청 횟수: 1 / 단계: 2
2번째 요청 마지막 메시지: 이전 응답이 비어 있었다. 하던 일을 이어서 ...
답변: A-1042는 배송 중이고 운송장 번호는 1234-5678-9012입니다.
```

여기서 확인할 것: 두 번째 요청이 새 user 메시지로 시작합니다. 빈 assistant는 이력에 없습니다.

이 처방은 마지막 수단으로 쓰십시오. 빈 응답이 반복된다면 대화 구조에 문제가 있다는 뜻이므로, 연속 요청을 늘리기 전에 이력을 확인해야 합니다. 문서도 같은 순서를 권합니다. 구조를 먼저 고치고, 연속 요청은 그 뒤에도 안 될 때만 씁니다.

빈 응답이 자주 나는 자리를 미리 알아 두면 좋습니다. 도구 결과를 여러 개 보낸 직후, 긴 도구 결과를 붙인 직후, 그리고 앞 턴에서 이미 완결된 답을 받은 뒤입니다. 이 세 자리에서 빈 응답이 나오면 대화를 의심하십시오. 반대로 첫 요청에서 빈 응답이 나오는 경우는 드물고, 그때는 모델이나 상한 문제일 가능성이 큽니다.

연속 요청 문장도 설계입니다. "계속"이라는 한 단어보다, 무엇을 이어야 하는지 한 문장으로 적는 편이 낫습니다. 이 장의 상수는 "이전 응답이 비어 있었다. 하던 일을 이어서 진행하고, 도구 결과를 근거로 답해라"입니다. 빈 응답의 원인을 모델에게 알려 주는 문장이므로, 같은 빈 응답이 다시 와도 모델은 다음 턴에 다르게 행동할 수 있습니다.

## 06.6 잘림은 두 종류다

잘린 응답은 두 가지입니다. `max_tokens`는 우리가 정한 상한에 걸린 것이고, `model_context_window_exceeded`는 모델의 창이 찬 것입니다. 둘 다 "응답이 완성되지 않았다"는 점은 같지만 대응이 다릅니다. 전자는 상한을 올리면 되고, 후자는 일을 쪼개야 합니다.

`max_tokens`에서 조심할 것은 **잘린 도구 호출**입니다. 응답이 도중에 끊기면 `tool_use` 블록의 인자가 미완성일 수 있습니다. 그 상태로 도구를 실행하면 오류가 나거나, 더 나쁘게는 엉뚱한 인자로 실행됩니다. 문서는 이때 상한을 올려 같은 요청을 다시 보내라고 안내합니다. 이 장의 코드는 두 값을 같은 예외로 묶고, 메시지에 어느 쪽인지 적습니다.

```python
if stop in ("max_tokens", "model_context_window_exceeded"):
    raise Truncated(f"응답이 잘렸다: {stop}. 상한을 올리거나 일을 쪼갠다.")
```

여기서 확인할 것: 두 값을 한 예외로 묶되, 로그에는 구분해 남깁니다. 나중에 원인을 볼 때 이 구분이 필요합니다.

상한을 올리는 일은 비용과 직결됩니다. 3장에서 본 것처럼 출력 단가가 입력보다 비싸고, 생각 토큰도 출력에 포함됩니다. 상한을 두 배로 올리면 잘림은 줄지만 평균 비용도 오릅니다. 그래서 상한은 "가장 긴 정상 응답"에 맞추고, 그보다 긴 응답이 필요하면 일을 쪼개는 편이 낫습니다.

창이 찬 경우는 다릅니다. 이것은 상한을 올려도 해결되지 않습니다. 대화가 길어서 창을 채운 것이므로, 이력을 줄이거나 일을 나눠야 합니다. 27장의 압축과 30장의 서브에이전트 위임이 그 자리에 쓰입니다. 지금은 두 이름을 구분해 로그에 남기는 것만으로 충분합니다. 잘림 로그에 두 값이 섞여 있으면, 나중에 어느 쪽을 고쳐야 할지 알 수 없습니다.

잘린 응답을 사용자에게 보내는 일은 없어야 합니다. 5장의 초안은 그것을 그대로 반환했습니다. 문장이 중간에서 끊긴 답은 오류보다 나쁩니다. 고객은 그것을 완성된 답으로 읽고, 없는 운송장 번호를 기다립니다.

실무에서는 세 가지를 함께 정합니다. 상한, 재시도 횟수, 그리고 재시도해도 안 될 때의 안내 문장입니다. 상한을 올려 한 번 더 시도하고, 그래도 잘리면 "답이 길어 나누어 안내하겠다"고 말한 뒤 짧게 다시 답합니다. 이 세 가지를 정해 두지 않으면, 잘림이 날 때마다 담당자가 즉석에서 판단하게 됩니다.

## 06.7 재개 지점을 남긴다

루프가 중간에 멈추면 그때까지의 대화를 어딘가에 남겨야 합니다. 남기지 않으면 다음 실행은 처음부터 다시 시작하고, 이미 지불한 토큰을 다시 지불합니다. 게임의 세이브와 비슷합니다. 세이브가 없으면 보스를 다시 잡아야 합니다. 이 비유가 맞는 곳은 "상태를 남기면 이어서 할 수 있다"는 점입니다. 깨지는 곳은 파일입니다. 게임은 세계 전체를 저장하지만, 우리가 저장하는 것은 대화와 단계뿐이고 도구가 바꾼 바깥 상태는 저장되지 않습니다.

재개 지점은 도구 결과를 받은 직후가 가장 좋습니다. 그 시점의 이력은 짝이 맞고, 다음 요청을 그대로 보낼 수 있습니다. 저장할 것은 네 가지입니다. 세션 식별자, 메시지 목록, 지금까지의 단계 수, 그리고 각 도구 결과를 받은 시각입니다.

```python
checkpoint = {
    "session_id": session_id,
    "messages": messages,
    "step": step,
    "tool_results": [{"tool_use_id": b["tool_use_id"], "name": name, "fetched_at": now}],
}
```

여기서 확인할 것: `fetched_at`입니다. 이것이 없으면 이어 달린 세션이 그 결과를 언제 받았는지 알 수 없습니다. 11장에서 이 값으로 오래된 결과를 가려냅니다.

시각을 남기는 이유는 신선도 때문입니다. 세 시간 뒤에 이어 달리는 것과 사흘 뒤에 이어 달리는 것은 다릅니다. 배송 상태는 하루면 바뀌고, 환불 이력은 한 달이 지나도 그대로입니다. 어느 결과를 다시 확인할지는 이 시각과 결과의 성격으로 정합니다.

저장하지 말아야 할 것도 있습니다. API 키, 세션 토큰, 고객의 카드 번호처럼 비밀번호에 준하는 값은 대화와 함께 저장하지 마십시오. 대화에는 도구 결과가 그대로 들어 있고, 도구 결과에는 그런 값이 섞이기 쉽습니다. 저장 전에 마스킹하는 단계를 두는 편이 낫습니다. 9장의 정규화가 그 자리에서 쓰입니다.

저장 위치도 정해야 합니다. 로컬 파일은 개발에 편하고, 운영에서는 여럿이 같은 세션을 이어 가지 않도록 잠금이 필요합니다. 두 프로세스가 같은 세션을 동시에 이어 가면 같은 도구를 두 번 실행합니다. 쓰기 도구라면 그것이 곧 두 번의 환불입니다. 11장에서 이 문제를 다룹니다.

## 06.9 검증한 것과 하지 못한 것

검증한 것은 루프의 분기입니다. `pause_turn`에서 내용을 그대로 돌려보내는지, 거절에서 모델만 바뀌는지, 빈 응답에서 이력에 빈 턴이 남지 않는지, 상한이 실제로 멈추는지를 대본으로 확인했습니다. 이 네 가지는 모델의 지능과 무관하게 코드가 결정하므로 대본으로 충분합니다.

하지 못한 것은 실제 발생입니다. 이 환경에는 API 키가 없어 `pause_turn`과 `refusal`을 실제로 유발하지 못했습니다. 서버 도구를 쓰지 않는 요청에서는 `pause_turn`이 나오지 않고, 거절은 정책에 닿는 요청에서만 나옵니다. 실제 호출에서 이 값들을 만나면 그 응답을 그대로 대본으로 저장해 두십시오. 그것이 가장 값싼 회귀 테스트가 됩니다.

또 하나 밝혀 둘 것이 있습니다. 이 장의 대체 모델은 고정값입니다. 실제 운영에서는 거절 분류에 따라 대체 모델을 달리 잡습니다. 가벼운 거절은 같은 계열의 다른 모델로 충분하고, 복잡한 판단이 필요한 거절은 상위 모델이 필요합니다. 이 연결표는 3장의 역할 표에 한 줄을 더하는 것으로 관리하십시오.

## 06.10 이 개념이 프로덕션에서 커지는 지점

여기서 만든 재개 지점은 11장에서 세션으로 커집니다. 저장한 네 값을 파일로 두면 프로세스가 죽어도 이어 달릴 수 있고, 복사하면 갈래 탐색이 됩니다. 9장의 게이트도 이 구조 위에 놓입니다. 승인 대기로 멈춘 루프는 세션을 저장하고 기다렸다가, 승인이 오면 그 지점에서 다시 시작합니다.

운영에서는 이 장의 네 분기가 장애의 절반을 설명합니다. 루프가 멈춘 것처럼 보이는데 아무 일도 안 했다면 `pause_turn`이나 빈 `end_turn`이고, 답이 중간에서 끊겼다면 잘림입니다. 이 네 이름을 알고 로그에 남기면 원인을 찾는 시간이 크게 줄어듭니다.

이 장의 루프는 아직 한 문의를 한 번에 처리합니다. 다음 장에서 이 루프를 여러 개 두고 조율하면, 여기서 만든 예외들이 조율자까지 올라와야 합니다. 서브에이전트가 멈춘 것을 조율자가 "보고가 없다"로만 알면 원인을 잃습니다. 7장의 보고서 형식에 이 장의 예외 이름을 넣는 이유가 그것입니다. 29장에서는 이 전파를 본격적으로 다룹니다.

정리하면 이렇습니다. 루프는 끝났다는 신호 하나만 읽는 장치가 아니라, 일곱 가지 멈춤을 구분해 각기 다르게 대응하는 장치입니다. 그 구분이 없으면 정상 경로는 돌아가도, 정상이 아닌 날에는 아무 설명도 남지 않습니다.
