## 34.1 이 장에서 만드는 것

이 장을 마치면 사내 도구 저장소 하나를 손에 갖게 됩니다. 이름은 `triage-tool`이고, 고객 문의를 분류해 상담원에게 넘기는 일을 합니다. 저장소에는 열 개의 파일이 들어갑니다. 규칙 문서, 스킬, 정책표, 훅, 경로 규칙, 이슈 템플릿, CI 워크플로, 작업 상태 파일 두 개입니다. 이 열 개가 **한 사람의 머릿속 절차를 팀의 절차로** 바꿉니다.

33장에서 "무엇이 좋은가"를 숫자로 정했습니다. 이 장은 그 기준을 지키도록 **권한과 절차**를 묶는 일입니다. 평가가 통과해도 실행 권한이 열려 있으면 사고는 다른 곳에서 납니다. 모델이 `rm -rf`를 부르거나 `.env`를 읽는 일은 품질 점수와 무관하게 일어납니다.

17~19장에서 CLAUDE.md, 스킬, 경로 규칙을 각각 배웠고, 21장에서 CI를 붙였습니다. 이 장은 그 부품을 한 저장소에 조립합니다. 새 개념은 하나입니다. **훅(hook)** 입니다. 훅은 Claude Code의 생명주기 특정 지점에서 우리 코드를 대신 실행하는 장치이고, `PreToolUse`는 도구 호출이 실행되기 전에 끼어들어 막을 수 있습니다.

이 장을 읽고 나면 새 도구를 하나 더 붙일 때 무엇을 어디에 적어야 하는지 알게 됩니다. 판단이 바뀌면 표를, 절차가 바뀌면 스킬을, 금지가 바뀌면 훅과 권한 설정을 고칩니다. 세 곳을 구분하는 것이 이 장의 핵심입니다.

사내 도구는 공개 도구와 다른 점이 셋 있습니다. 데이터가 밖으로 나가면 안 되고, 쓰는 사람이 정해져 있고, 만든 사람과 쓰는 사람이 다릅니다. 세 번째가 가장 어렵습니다. 만든 사람은 구조를 알지만 쓰는 사람은 모르므로, 규칙이 코드에만 있으면 쓰는 사람은 왜 막혔는지 알 수 없습니다. 그래서 이 장은 규칙을 문서와 표와 이슈 폼에 나눠 남깁니다.

## 34.2 요구사항 세 문장에서 시작한다

이 장의 출발점은 코드가 아니라 요구사항 세 문장입니다. 첫째, 상담원이 같은 질문을 두 번 하지 않게 한다. 둘째, 사고를 낼 수 있는 명령은 애초에 실행되지 않게 한다. 셋째, 새로 온 사람이 첫날 같은 방식으로 일하게 한다. 이 세 문장이 저장소의 구조를 정합니다.

첫 문장은 **패킷**이 답합니다. 28장에서 만든 아홉 칸짜리 문서를 이슈로 만들면 상담원은 처음부터 다시 묻지 않습니다. 둘째 문장은 **훅과 권한 설정**이 답합니다. 셋째 문장은 **CLAUDE.md와 스킬**이 답합니다. 같은 요구사항을 세 부품이 나눠 맡는 구조입니다.

요구사항은 평가 기준도 만듭니다. "같은 질문을 두 번 하지 않는다"는 패킷의 빈 칸 수로, "사고 명령이 실행되지 않는다"는 훅 판정 11건으로, "첫날 같은 방식으로 일한다"는 새 세션에서 같은 파일이 만들어지는지로 잽니다. 33장의 게이트가 이 세 가지를 회귀 검사로 돌립니다. 요구사항이 숫자로 바뀌지 않으면, 문서를 예쁘게 쓰고 끝납니다.

조립 순서는 정해 두는 편이 좋습니다. 요구사항 → 정책표 → 훅 → 스킬 → 규칙 문서 → 이슈 템플릿 → CI 순입니다. 반대로 문서부터 쓰면, 아직 정하지 않은 판단을 문장으로 채우게 됩니다. 표를 먼저 쓰면 "이 줄은 누가 판단하는가"에 답하지 못하는 항목이 드러납니다.

### 34.2.1 네 부품의 역할

부품이 겹치면 나중에 어느 쪽이 이기는지를 아무도 모릅니다. CLAUDE.md에 "파일을 만들지 마십시오"라고 적고 스킬에는 파일 만드는 도구를 허용하면, 모델은 둘 중 하나를 골라 따릅니다. 이 장은 역할을 이렇게 나눕니다. CLAUDE.md는 **일하는 방식**, 경로 규칙은 **디렉터리별 관례**, 스킬은 **한 업무의 절차**, 정책표와 훅은 **금지와 판정**입니다. 같은 내용을 두 곳에 적지 않는 것이 유지보수의 핵심입니다.

비유하면 사내 출입 절차입니다. 교육으로 "위험한 곳에 들어가지 마십시오"라고 알리고, 출입카드로 실제로 막습니다. 교육만 있으면 바쁜 날에 잊고, 카드만 있으면 왜 막혔는지 모릅니다. 이 비유가 맞는 곳은 **안내와 강제가 서로를 보완한다**는 점입니다. 깨지는 곳은 예외 처리입니다. 출입카드는 총무가 예외를 열지만, 우리 훅의 예외는 코드에 적힌 규칙이라 아무나 열 수 없습니다. 그래서 예외를 여는 절차를 따로 정해야 합니다.

## 34.3 프롬프트만으로는 왜 부족한가

CLAUDE.md에 "위험한 명령을 실행하지 마십시오"라고 적으면 대부분의 날에는 지켜집니다. 문제는 지켜지지 않는 날입니다. 9장에서 본 것처럼 안내는 모델의 판단에 맡기고, 강제는 코드가 거부합니다. 보안에서 이 둘을 같은 것으로 보면 안 됩니다.

실제 사고는 대개 작은 요청에서 시작합니다. "환불 규정 확인해 줘"라는 요청에 모델이 관련 설정을 찾겠다고 `.env`를 열고, 그 안의 토큰이 대화 기록에 남습니다. 이 장의 설정은 이 호출을 두 겹으로 막습니다. 권한 설정의 `Read(./.env)` 거부가 먼저 막고, 훅의 P4가 같은 파일 쓰기를 한 번 더 막습니다. 두 겹이 겹치는 것은 낭비가 아니라, 한 겹이 설정 오타로 사라져도 다른 겹이 남게 하는 장치입니다.

이 장의 훅은 도구 호출 하나하나를 표에 비춥니다. 11개 호출을 넣어 보면 6건이 거부되고, 4건이 허용되고, 1건이 확인 요청으로 갑니다. 거부된 6건에는 `rm -rf`, `git push`, `curl | sh`, `.env` 쓰기, 저장소 밖 경로 쓰기가 들어 있습니다. 사람이 봐야 할 것은 판정문이 아니라 **표에 없는 호출**입니다. 표에 없는 호출은 허용되므로, 표가 낡으면 구멍이 됩니다.

판정을 세 가지로 나누는 이유도 분명합니다. `git push`를 막는 것은 이 저장소가 풀 리퀘스트로만 바뀌기 때문이고, `create_report`를 `ask`로 두는 것은 금지할 일은 아니지만 사용자가 요청하지 않았을 때 파일이 생기면 안 되기 때문입니다. 금지와 확인은 다릅니다. 금지를 확인으로 바꾸면 사람이 매번 눌러야 하고, 확인을 금지로 바꾸면 필요한 작업이 막힙니다.

### 34.3.1 정책표는 코드 밖에 둔다

정책표를 파이썬 `if` 문으로 쓰면 업무 담당자가 고칠 수 없습니다. 그래서 표는 `docs/policy.json`에 두고, 훅은 표를 읽어 판정만 합니다. 표의 각 줄은 아이디, 조건, 판정, 이유 네 칸입니다. 아이디가 있어야 이슈와 로그에서 "P1에 걸렸다"고 말할 수 있습니다.

```json
{
  "id": "P1",
  "match": {"tool": "Bash", "command_any": ["rm -rf", "mkfs", "dd if="]},
  "action": "deny",
  "reason": "파괴적 명령은 사람이 직접 실행한다"
}
```

이 블록이 하는 일: 정책표의 한 줄입니다. Bash 명령에 `rm -rf` 같은 문자열이 들어 있으면 거부합니다.

여기서 확인할 것: 조건이 `tool`과 `command_any` 두 개이고, 둘 다 맞아야 걸립니다. `Read` 도구로 `rm -rf`라는 파일을 읽는 것은 막지 않습니다. 조건을 넓게 잡으면 정상 작업이 막히고, 좁게 잡으면 구멍이 남습니다. 표를 고칠 때는 이 균형을 봅니다.

표의 소유자도 정합니다. 이 장의 표에는 `"owner": "support-ops"`가 적혀 있습니다. 업무가 표를 소유하고, 엔지니어는 표를 읽는 코드만 유지합니다. 표를 바꾼 날짜와 사유를 함께 남기면, 나중에 "언제부터 이 호출이 막혔나"를 답할 수 있습니다. 표의 한 줄이 곧 정책의 단위이고, 그 줄의 아이디가 대화와 로그와 이슈를 이어 주는 열쇠입니다.

## 34.4 훅 — 도구 호출을 가로채는 자리

훅은 설정 파일에 등록합니다. `PreToolUse`에 matcher로 도구 이름을 적고, 실행할 명령을 답니다. matcher는 정규식처럼 동작하므로 `Bash|Write|Edit`처럼 묶을 수 있습니다.

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash|Write|Edit|mcp__docs-hub__create_report|escalate_to_human",
      "hooks": [{
        "type": "command",
        "command": "python3 \"${CLAUDE_PROJECT_DIR}/.claude/hooks/policy_gate.py\""
      }]
    }]
  }
}
```

이 블록이 하는 일: 도구 호출 전에 정책 게이트를 실행하도록 등록합니다. 경로는 프로젝트 루트 기준입니다.

여기서 확인할 것: `matcher`에 MCP 도구와 우리 도구까지 넣었습니다. matcher를 `Bash`로만 두면 파일 쓰기와 에스컬레이션은 검사 없이 지나갑니다. 훅은 matcher에 걸린 호출에만 실행되므로, 목록이 곧 검사 범위입니다.

### 34.4.1 훅의 입력과 판정

훅은 표준 입력으로 호출 정보를 JSON으로 받고, 표준 출력으로 판정을 돌려줍니다. 판정은 `allow`, `deny`, `ask` 세 가지입니다. `deny`는 실행을 막고 이유를 모델에게 보여 줍니다. 모델은 그 이유를 읽고 다른 방법을 찾습니다. 이유가 "권한 없음"처럼 짧으면 모델은 같은 호출을 반복하고, 이유가 구체적이면 우회로를 찾습니다.

출력의 모양도 지켜야 합니다. 판정은 `hookSpecificOutput` 안에 `permissionDecision`과 `permissionDecisionReason`으로 넣습니다. 형식이 틀리면 Claude Code는 그 훅의 판정을 읽지 못하고, 훅이 없는 것과 같은 상태가 됩니다. 그래서 이 장의 검사는 함수 호출만 보지 않고 생성된 훅을 실제 프로세스로 실행해 출력까지 확인합니다.

matcher에는 MCP 도구의 전체 이름을 적어야 합니다. MCP 도구는 `mcp__서버이름__도구이름` 형식이므로, `create_report`만 적으면 걸리지 않습니다. 32장에서 `allowed_tools`에 같은 형식을 쓴 것과 같습니다. 이름을 줄여 쓰는 습관이 훅을 조용히 비켜 가게 만듭니다.

```python
def decide(event: dict, rules: list[dict]) -> dict:
    """도구 호출 하나를 표에 비추어 allow / deny / ask로 판정한다."""
    tool = event.get("tool_name", "")
    tool_input = event.get("tool_input", {})
    if tool == "escalate_to_human":
        if missing := missing_packet(tool_input):
            return {"decision": "deny", "rule": "P7",
                    "reason": "에스컬레이션 패킷 칸이 비었다: " + ", ".join(missing)}
        return {"decision": "allow", "rule": "P7", "reason": "패킷 9칸이 모두 찼다"}
    for rule in rules:
        if _matches(rule, tool, tool_input):
            return {"decision": rule["action"], "rule": rule["id"], "reason": rule["reason"]}
    return {"decision": "allow", "rule": "-", "reason": "표에 걸리는 줄이 없다"}
```

이 블록이 하는 일: 도구 이름과 인자를 받아 표를 순서대로 적용하고, 처음 걸리는 줄의 판정을 돌려줍니다. 에스컬레이션 도구만 표보다 먼저 특별 검사를 합니다. 여기서 붙는 P7은 표에 없는 코드 수준의 규칙입니다. 패킷 아홉 칸은 업무 판단이 아니라 도구의 계약이므로, 표가 아니라 코드에 둡니다.

여기서 확인할 것: 표에 걸리는 줄이 없으면 허용입니다. 그래서 표의 마지막 줄에 "그 밖의 사유"를 두는 28장의 규칙이 여기서는 **허용**으로 뒤집힙니다. 위험한 쪽은 허용이므로, 새 도구를 붙이는 날에는 표에 줄을 먼저 추가해야 합니다.

훅은 만능이 아닙니다. 훅 자체가 실패하면 Claude Code는 그 실패를 어떻게 처리할지 설정에 따라 다르게 다룹니다. 이 장의 게이트는 예외를 잡아 `deny`로 닫는 편이 안전합니다. 열린 채로 실패하면 표가 없는 것과 같습니다.

비용도 생각해야 합니다. 훅은 도구 호출마다 프로세스 하나를 띄웁니다. 모델 호출이 아니라 로컬 프로세스이므로 밀리초 단위로 끝나지만, 호출이 수백 번인 작업에서는 수 초가 됩니다. 훅 안에서 네트워크를 부르거나 파일을 크게 읽으면 그 시간이 그대로 대화 지연이 됩니다. 훅은 표를 읽고 문자열을 비교하는 정도로 가볍게 두십시오.

훅의 시험은 호출 이벤트를 파일로 만들어 두는 것으로 시작합니다. 도구 이름과 인자만 있는 작은 JSON이면 충분하고, 기대 판정을 함께 적으면 회귀 시험이 됩니다. 이 장의 11건이 그 목록입니다. 새 규칙을 넣을 때마다 그 규칙을 건드리는 이벤트를 한 건씩 더하십시오. 규칙과 시험이 함께 늘어야 표가 낡지 않습니다.

쉽게 말해, 훅은 문 앞에 세운 경비원이 아니라 문에 달린 잠금장치입니다. 경비원은 그날 기분에 따라 놓칠 수 있지만, 잠금장치는 열쇠가 맞지 않으면 열리지 않습니다. 대신 잠금장치는 왜 안 열리는지를 말해 주지 않으므로, 이유는 우리가 적어 주어야 합니다.

## 34.5 스킬 — 절차를 한 파일로 묶는다

스킬은 `SKILL.md` 한 파일입니다. 앞부분에 이름과 설명을 적고, 본문에 절차를 씁니다. Claude Code는 스킬의 이름과 설명을 항상 문맥에 두고, 필요할 때 본문을 읽습니다. 그래서 **설명이 곧 호출 조건**입니다. 18장에서 본 성질이 여기서는 "언제 이 절차를 따르는가"를 정합니다.

```text
---
name: triage-escalate
description: 고객 문의를 분류해 에스컬레이션 패킷을 만들고 사람에게 넘긴다. 정책 공백, 규정에 없는 예외 요청, 법적 조치 언급, 담당자 판단이 필요한 건에 사용한다.
allowed-tools: Read, Grep, mcp__docs-hub__search_docs, mcp__docs-hub__get_doc, escalate_to_human
---
```

이 블록이 하는 일: 스킬의 머리말입니다. 이름, 설명, 이 스킬에서 쓸 수 있는 도구를 적습니다.

여기서 확인할 것: `allowed-tools`에 쓰기 도구가 없습니다. 이 스킬은 패킷을 만들 뿐 파일을 만들지 않습니다. 권한을 좁히면 오선택도 함께 줄어듭니다. 32장에서 `create_report`를 기본 허용 목록에서 뺀 것과 같은 판단입니다.

본문에는 여섯 단계가 들어갑니다. 원문에서 케이스와 고객의 말을 옮기고, 정책표를 순서대로 적용하고, 걸린 줄이 없으면 `policy_gap`으로 두고, 금액은 원문에 있을 때만 채우고, 아홉 칸을 모두 채워 도구를 부르고, 넘긴 뒤 한 줄을 남깁니다. 절차의 각 단계가 28장의 판단과 대응합니다.

스킬과 슬래시 커맨드는 다릅니다. 커맨드는 사용자가 이름을 불러야 시작하고, 스킬은 설명을 읽은 모델이 필요하다고 판단할 때 스스로 읽습니다. 그래서 스킬의 설명에는 **언제 쓰는가**와 **언제 쓰지 않는가**가 함께 들어가야 합니다. 이 장의 설명은 "정책 공백, 규정에 없는 예외 요청, 법적 조치 언급, 담당자 판단이 필요한 건"을 나열해 호출 조건을 좁힙니다. "문의를 처리한다"처럼 넓게 쓰면 모든 문의에 이 스킬이 붙고, 그만큼 다른 절차가 밀립니다.

설명의 길이도 예산입니다. 이 스킬의 설명은 87자입니다. 스킬이 열 개 붙으면 설명만 870자가 매 턴 문맥에 남습니다. 스킬을 많이 만들수록 설명을 짧고 구분되게 써야 합니다. 설명이 서로 비슷하면 모델은 엉뚱한 스킬을 읽고, 그 비용은 본문 토큰으로 돌아옵니다.

본문은 길어도 됩니다. 스킬의 본문은 호출될 때만 읽히므로, 절차를 자세히 적어 둘수록 좋습니다. 흔한 실수는 반대입니다. 설명에 절차를 몰아넣어 매 턴 문맥을 차지하게 하고, 본문은 비워 두는 경우입니다. 설명은 문을 여는 열쇠이고, 본문은 문 안의 안내판입니다.

## 34.6 패킷을 이슈 템플릿으로 바꾼다

28장의 패킷은 사람에게 건네는 문서였습니다. 같은 것을 GitHub 이슈 폼으로 만들면 패킷이 **기록**이 됩니다. 누가 언제 넘겼고 무엇을 결정했는지가 저장소에 남고, 다음 사람은 같은 양식으로 읽습니다.

폼의 칸은 패킷의 아홉 칸과 정확히 같아야 합니다. 케이스 아이디, 범주, 심각도, 금액, 고객의 말, 걸린 정책, 확인한 것, 왜 사람, 다음에 할 일입니다. 칸이 하나라도 다르면 사람이 두 곳을 오가며 옮겨 적게 됩니다. 이 장의 검사는 폼의 칸 목록과 코드의 `PACKET_FIELDS`가 같은지 확인합니다.

```python
def render_packet(packet: dict) -> str:
    """패킷 아홉 칸을 이슈 본문으로 바꾼다. 빈 칸은 '원문에 없음'으로 적는다."""
    labels = [("case_id", "케이스"), ("category", "범주"), ("severity", "심각도"),
              ("amount", "금액"), ("customer_words", "고객의 말"), ("policy_rule", "걸린 정책"),
              ("checked", "확인한 것"), ("why_human", "왜 사람"), ("next_action", "다음에 할 일")]
    lines = ["### 에스컬레이션 패킷", ""]
    for key, label in labels:
        value = packet.get(key)
        if value in (None, ""):
            value = "원문에 없음"
        lines.append(f"- **{label}**: {value}")
    return "\n".join(lines)
```

이 블록이 하는 일: 패킷 딕셔너리를 이슈 본문 마크다운으로 바꿉니다.

여기서 확인할 것: `None`과 빈 문자열을 "원문에 없음"으로 바꿉니다. 빈 칸으로 두면 상담원은 그 칸이 없는 줄 모르고 지나갑니다. 28장에서 "빈 칸 대신 모른다를 적는다"고 한 규칙이 코드가 됩니다.

폼에는 `required: true`를 걸어 빈 제출을 막습니다. 다만 "원문에 없음"은 빈 값이 아니므로 통과합니다. 이것이 의도입니다. 모르는 것을 모른다고 적은 패킷은 좋은 패킷이고, 빈 패킷은 나쁜 패킷입니다.

이슈는 넘기고 끝나지 않습니다. 상담원이 결정을 적고 닫으면, 그 결정이 정책표를 고치는 재료가 됩니다. 같은 `policy_gap`이 한 달에 다섯 번 올라오면 규정을 만들어 표에 한 줄을 추가할 때입니다. 그때 33장의 골든셋에도 그 건을 넣습니다. 넘김 → 결정 → 규정 → 시험지 → 다음 배포가 한 바퀴로 이어집니다.

폼의 칸 이름은 코드의 필드 이름과 같게 두는 것이 좋습니다. `case_id`, `why_human`처럼 영문 식별자를 쓰면, 이슈 본문을 파싱해 대시보드로 보낼 때 이름을 바꾸지 않아도 됩니다. 사람이 보는 라벨은 한국어로 두고, 식별자만 영문으로 통일하십시오. 이 장의 폼이 그 방식입니다.

폼은 사람 사이의 계약이기도 합니다. 상담원이 "왜 사람인가"를 읽고 바로 판단할 수 있으면 넘김이 성공이고, 그 칸이 비어 있으면 넘김이 실패입니다. 그래서 이 폼은 입력 양식이 아니라 **품질 기준**입니다.

고객의 말은 원문으로 넣되, 개인정보는 줄입니다. 28장에서 "고객의 말만 원문으로"라고 한 것은 문장의 결을 살리기 위해서이지, 전화번호와 계좌번호까지 옮기라는 뜻이 아닙니다. 이슈는 저장소 권한이 있는 사람 누구나 읽습니다. 35장에서 이 축소를 코드로 다룹니다.

닫힌 이슈를 세는 일도 자동화할 수 있습니다. 라벨별로 몇 건이 올라왔고 평균 처리 시간이 얼마인지는 저장소 API로 셀 수 있습니다. 이 숫자가 오르면 사람이 병목이고, 줄면 자동 판정이 자리를 잡은 것입니다.

## 34.7 큰 저장소의 운용을 저장소에 심는다

30장의 manifest와 스크래치패드는 사람이 기억해야 하는 절차였습니다. 기억은 다음 사람에게 전달되지 않습니다. 그래서 이 장은 그 절차를 CLAUDE.md에 적고, 상태 파일을 저장소에 둡니다. `state/manifest.json`에는 이번 작업의 파일 목록과 읽음 표시가, `state/scratchpad.md`에는 완료·다음·결정이 들어갑니다.

CLAUDE.md는 짧게 유지합니다. 이 장이 만든 파일은 26줄, 788자입니다. 다섯 단계의 작업 절차, 네 가지 금지, 세 개의 참고 경로가 전부입니다. CLAUDE.md가 길어지면 매 세션 문맥을 차지하고, 길어진 규칙은 서로 충돌합니다. 자세한 내용은 스킬과 경로 규칙으로 보냅니다.

경로 규칙은 `.claude/rules/paths.md`에 둡니다. `src/**/*.py`와 `tests/**/*.py`에만 적용되는 규칙을 적고, 앞부분의 `paths`에 그 범위를 씁니다. 19장에서 본 조건부 로딩입니다. `src/`에서는 예외 대신 결과 객체를 돌려주고, `tests/`에는 실제 고객 문장을 넣지 않는다는 규칙이 여기 들어갑니다.

`/compact`와의 관계도 적어 둡니다. 대화가 길어져 압축이 일어나기 전에 팩트 블록과 결정을 파일로 옮기라는 한 줄입니다. 27장과 30장의 결론이 문서 한 줄로 남으면, 새 세션이 같은 실수를 덜 합니다.

CLAUDE.md의 계층도 알고 있어야 합니다. 사용자 수준 문서는 내 컴퓨터의 모든 프로젝트에, 프로젝트 문서는 이 저장소에, 디렉터리 문서는 그 폴더에 적용됩니다. 팀 규칙은 반드시 프로젝트 문서에 두십시오. 사용자 수준에 두면 동료에게 가지 않고, 디렉터리 문서에 두면 루트에서 시작한 작업이 읽지 못합니다.

새로 온 사람이 첫날 이 저장소를 열면 CLAUDE.md의 다섯 단계를 읽고, 스킬이 절차를 알려 주고, 훅이 금지를 지켜 줍니다. 문서를 따로 읽히지 않아도 같은 방식으로 일하게 만드는 것이 목표입니다. 온보딩 문서를 하나 더 만드는 대신 저장소 자체를 온보딩 문서로 쓰는 편이 낫습니다.

상태 파일은 커밋하지 않는 편이 좋습니다. `state/`의 내용은 작업 중인 사람마다 다르고, 커밋하면 충돌만 만듭니다. 대신 양식만 저장소에 두고, 실제 파일은 `.gitignore`에 넣습니다. 다음 세션은 양식을 보고 자기 상태를 채웁니다.

## 34.8 CI에 붙인다

훅과 규칙은 로컬에서만 돌면 우회됩니다. 저장소에 들어온 변경은 CI에서 같은 검사를 통과해야 합니다. 이 장의 워크플로는 풀 리퀘스트마다 `verify.py`를 돌립니다. `verify.py`는 정책 판정 11건, 패킷 검사, 이슈 폼 일치, 생성된 훅의 실제 실행을 확인합니다.

CI가 확인해야 할 것은 코드의 문법이 아니라 **규칙의 일치**입니다. 정책표에 줄을 추가했는데 이슈 폼에 칸을 안 늘렸다든가, 스킬 설명을 바꿨는데 트리거가 사라졌다든가 하는 어긋남이 실제 사고를 만듭니다. 이 장의 검사가 그 어긋남을 잡습니다.

CI에 비밀 값을 넣지 않는 것도 규칙입니다. 이 워크플로는 API 키가 필요 없습니다. 모델 호출은 대본으로 대체되고, 판정은 순수 함수입니다. 평가와 게이트를 키 없이 돌 수 있게 만들어 두면, 포크 저장소에서도 같은 검사가 돕니다.

드리프트도 CI가 잡습니다. 정책표에 줄을 추가했는데 권한 설정의 `deny` 목록에 반영되지 않았거나, 스킬에서 도구 이름을 바꿨는데 `allowed-tools`가 옛 이름을 가리키는 상태가 대표적입니다. 이런 어긋남은 로컬에서는 잘 드러나지 않고, 몇 달 뒤 사고로 드러납니다. CI가 매 변경마다 두 파일을 대조하면 그 사이에 고칠 기회가 생깁니다.

이 검사를 필수 검사로 등록하면 우회가 어려워집니다. 저장소 설정에서 해당 워크플로를 필수로 두고, 관리자도 예외로만 통과하게 하십시오. 규칙은 사람이 지키는 것이 아니라 통과해야 하는 관문이어야 합니다.

## 34.10 흔한 실패 여덟 가지

첫째, 훅을 `Bash`에만 겁니다. 파일 쓰기와 MCP 도구가 검사 밖으로 나갑니다. matcher에 검사할 도구를 모두 적으십시오.

둘째, 정책표를 코드에 복제합니다. 표와 코드가 두 곳이 되면 반드시 어긋나고, 어긋난 쪽이 조용히 이깁니다. 표는 한 곳에만 둡니다.

셋째, 거부 이유를 짧게 씁니다. "권한 없음"은 모델에게 다음 행동을 주지 않아 같은 호출을 반복하게 합니다. 표의 `reason`을 그대로 보여 주십시오.

넷째, 패킷을 빈 칸으로 넘깁니다. 상담원이 다시 묻고, 고객은 두 번 말합니다. "원문에 없음"을 값으로 인정하십시오.

다섯째, 스킬 설명을 길고 비슷하게 씁니다. 설명은 매 턴 문맥을 차지하고, 비슷하면 잘못 로딩됩니다.

여섯째, CLAUDE.md에 모든 것을 넣습니다. 200줄짜리 규칙 문서는 읽히지 않고, 충돌하는 규칙이 생깁니다.

일곱째, 훅을 CI에서 검사하지 않습니다. 로컬 훅은 설정을 바꾸면 사라집니다. 생성된 훅을 실제 프로세스로 실행하는 검사를 CI에 넣으십시오.

여덟째, 예외를 코드에 하드코딩합니다. "이 경우만 통과"를 `if`로 넣으면 그 예외가 영원히 남고, 표에는 보이지 않습니다. 예외가 필요하면 표에 만료일이 있는 줄로 넣으십시오. 코드에 숨은 예외는 다음 사람이 찾지 못합니다.

여덟 가지 중 다섯 가지가 "규칙을 두 곳에 두는 일"로 돌아갑니다. 표와 코드, 설명과 본문, 저장소와 개인 설정이 어긋나는 순간 게이트는 조용히 무력해집니다. 어긋남을 사람의 주의력으로 막지 말고 검사로 막으십시오.

- [ ] manifest와 스크래치패드가 저장소 안 `state/`에 있다.
