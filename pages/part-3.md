## Part III를 여는 글

Part II에서 우리는 일을 나누고, 넘기고, 막고, 이어 가는 구조를 세웠습니다. 조율자와 담당이 있고, 위임 패킷이 있고, 게이트가 있고, 세션이 있습니다. 그 구조에는 아직 빈자리가 하나 있습니다. **담당이 쥐고 있는 도구가 어떤 모양인가**입니다.

구조가 아무리 튼튼해도 도구의 이름과 설명이 어긋나면 담당은 엉뚱한 것을 부릅니다. Part II의 마지막 문장이 그것이었습니다. 좋은 구조가 좋은 선택을 보장하지는 않습니다. 이 파트의 다섯 장이 그 선택을 다룹니다.

이 파트는 시험의 두 번째 도메인인 **도구 설계와 MCP 통합(18%)** 을 맡습니다. 60문항으로 환산하면 약 11문항입니다. 다섯 장이 다섯 개 항목에 하나씩 대응하고, 순서도 항목 순서를 그대로 따릅니다. 인터페이스를 설계하고, 실패를 형식으로 만들고, 도구를 배분하고, MCP로 붙이고, 내장 도구를 고릅니다.

| 장 | 제목 | 얻게 되는 것 |
|---|---|---|
| 12 | 도구 인터페이스 설계 | "언제 쓰지 않는가"를 문장으로 밝힌 도구 정의와, 합칠 도구와 나눌 도구의 기준 |
| 13 | 구조화된 에러 응답 | 분류·재시도 가능 여부·힌트·부분 결과를 가진 실패 형식과 복구 정책 |
| 14 | 도구 배분과 `tool_choice` | 역할별로 자른 도구 목록과 단계별 선택 모드 결정표 |
| 15 | MCP 서버 통합 | `.mcp.json` 설정, 변수 확장, 세 프리미티브 사용법, 서버 쪽 게이트 |
| 16 | 내장 도구 | Read·Write·Edit·Bash·Grep·Glob의 실패를 읽고 탐색 순서를 세우는 눈 |

Part II에서 이어받는 것은 세 가지 연결점입니다. 7장의 `description`은 "무엇을 하는가"가 아니라 "언제 부르는가"라는 원칙, 9장의 "도구 이름을 한 곳에서 관리하고 별칭을 만들지 않는다"는 규칙, 8장 패킷의 `return_format`이 그것입니다. 12장은 첫 번째를 도구 전체로 넓히고, 13장은 6장의 예외 이름(`Truncated`·`Refused`·`StepLimit`)과 7장 보고서의 `status`를 도구 수준으로 내리고, 14장은 7장의 `tools` 최소 권한표와 8장의 `disable_parallel_tool_use` 조건을 이어받습니다.

Part IV로 넘기는 것은 **도구를 고르는 눈과 오류를 읽는 습관**입니다. Part IV의 Claude Code 설정은 결국 같은 질문을 다른 층에서 다시 합니다. 어떤 도구를 열어 줄 것인가(권한), 어떤 규칙을 미리 알려 줄 것인가(CLAUDE.md·스킬), 실패했을 때 무엇을 다시 시킬 것인가(훅·재시도)입니다. 15장에서 만든 `.mcp.json`은 17장의 프로젝트 설정과 같은 폴더에 놓이고, 16장의 내장 도구는 20장의 plan mode 판단에 그대로 쓰입니다.

준비물은 앞 파트와 같습니다. Python 3.12와 터미널이면 되고, API 키 없이 대본으로 돌아갑니다. 예제 폴더는 `work/ch12-tool-interface/`부터 `work/ch16-builtin/`까지이고, 다섯 폴더 모두 5장 폴더의 `schemas.py`·`tools.py`·`transport.py`를 불러다 씁니다. 각 폴더에서 `python3 verify.py`를 실행하면 이 장들의 로그가 그대로 나옵니다. 다섯 장을 읽는 데 3~4시간, 코드를 돌려 보면 5시간쯤 걸립니다.

읽는 순서에 한 가지를 권합니다. 12장과 13장은 한 쌍으로 읽으십시오. 설명이 선택을 정하고, 오류가 다음 선택을 정합니다. 이 둘이 도구 경험의 전부입니다. 14장과 15장도 한 쌍입니다. 14장이 "몇 개를 보여 줄 것인가"를, 15장이 "어디서 가져올 것인가"를 정합니다. 16장은 그 위에 얹히는 실무 도구입니다.

이 파트의 장들은 코드가 짧습니다. 짧은 대신 비교가 많습니다. 같은 네 가지 일을 좋은 설명과 모호한 설명으로 두 번 정의하고, 같은 실패를 문장 하나짜리 오류와 구조화된 오류로 두 번 돌리고, 같은 도구 목록을 역할별로 잘라 크기를 재고, 같은 서버를 정상 설정과 잘못된 설정으로 두 번 읽힙니다. 숫자가 나오는 자리가 곧 시험의 선택지가 갈리는 자리입니다.

시험에서는 "이 상황에서 무엇을 먼저 고칠 것인가"로 나옵니다. 도구가 엉뚱하게 불리면 설명을 고치고, 같은 실패가 반복되면 오류 형식을 고치고, 도구가 너무 많으면 목록을 자릅니다. 세 처방이 서로 다르다는 것을 아는 것이 이 파트의 성과입니다.

다섯 장을 다 읽으면 한빛몰의 지원 시스템은 도구 네 개를 가진 작은 시스템에서, 설명과 오류와 권한이 정리된 도구 묶음을 가진 시스템으로 바뀝니다. 그 묶음이 32장에서 실제 서버가 됩니다. 이 파트의 예제는 모두 같은 문서 네 건과 티켓 세 건을 씁니다. 데이터를 바꾸지 않고 도구의 겉모습만 바꾸는 이유는, 달라지는 것이 데이터가 아니라 데이터를 다루는 방식임을 보이기 위해서입니다.
