## 부록 E. 시험 범위 밖 실무 도구

이 부록은 시험이 묻지 않지만 현장에서 자주 만나는 도구를 다룹니다. 1장에서 본 범위 밖 목록과 35장의 실무 확장이 여기서 만납니다. 시험 준비 중이라면 읽지 않아도 됩니다. 다만 책을 덮은 뒤 첫 프로젝트를 시작할 때, 이 부록이 "다음에 무엇을 배울지"의 목록이 됩니다.

범위 밖이라는 표시는 무지의 고백이 아니라 시간 배분의 지시입니다. 시험을 준비하는 동안에는 이 도구들에 머물지 말고, 시험이 끝난 뒤에 돌아오십시오. 각 항목에 "시험과의 거리"를 적어 둔 이유도 그것입니다.

### E.1 입력을 넓히는 도구 — Vision과 Files

Vision은 이미지를 입력으로 받는 기능입니다. 영수증 사진, 화면 캡처, 도면, 표가 담긴 페이지가 여기에 해당합니다. 구조화 추출 파이프라인에서 스캔 문서를 다룰 때 실제로 쓰게 됩니다. 37장의 시나리오 D에 스캔 문서가 나오지만, 시험은 이미지 처리 자체를 묻지 않고 추출 설계를 묻습니다.

Files는 파일을 미리 올려 두고 요청에서 참조하는 기능입니다. 같은 문서를 여러 번 보낼 때 업로드를 반복하지 않아도 되고, 파일의 수명을 관리할 수 있습니다. 배치 작업이나 반복 평가에서 입력이 클 때 특히 유용합니다. 시험 범위 밖이므로 "이런 기능이 있다"까지만 알아 두십시오.

두 기능 모두 입력을 바꾸는 도구이지 판단을 바꾸는 도구가 아닙니다. 입력이 사진이라고 해서 추출 기준이 달라지지는 않습니다. 24장의 스키마와 25장의 검증은 그대로 적용됩니다.

### E.2 응답을 다루는 도구 — Streaming과 Citations

Streaming은 응답을 토큰 단위로 받아 화면에 먼저 보여 주는 방식입니다. 체감 지연을 줄이는 데 효과가 있고, 35장에서 본 것처럼 첫 토큰까지의 시간과 전체 완료 시간을 나눠 재야 합니다. 시험 범위 밖이지만 실무에서는 거의 기본값입니다. 사용자는 2초 안에 무언가 움직이는 것을 봐야 기다립니다.

Citations는 답변의 문장과 원문 구간을 연결해 주는 기능입니다. 31장의 출처 네 조각을 제품 기능으로 받는 셈입니다. 다만 인용이 붙었다고 해서 인용이 정확한 것은 아닙니다. 구간이 원문과 맞는지는 여전히 검사해야 하고, 그 검사가 33장의 그레이더입니다.

두 기능 모두 "보여 주는 방식"을 바꿉니다. 판단의 정확도는 프롬프트와 검증에서 나오고, 스트리밍과 인용은 그 판단을 사용자에게 전달하는 방식을 바꿉니다. 전달 방식을 먼저 다듬고 판단을 나중에 만드는 순서는 위험합니다.

### E.3 실행 환경을 맡기는 도구 — Managed Agents와 MCP 터널

Managed Agents는 에이전트의 실행 환경을 Anthropic이 호스팅하는 표면입니다. 서버를 직접 띄우지 않고 루프를 돌릴 수 있어, 초기 구축의 부담이 줄어듭니다. 대신 실행 환경에 대한 통제가 줄어들고, 사내 데이터의 위치와 보존을 확인해야 합니다. 2장에서 표면을 "누가 루프를 돌리는가"로 구분한 기준이 여기에도 적용됩니다.

MCP 터널은 사내망의 서버를 밖으로 노출하지 않고 연결하는 통로입니다. 포트를 여는 대신 터널을 쓰면, 인증과 접근 통제를 한 곳에서 관리할 수 있습니다. 32장에서 배포를 stdio에서 원격으로 옮길 때 마지막 단계가 이 선택이었습니다.

이 두 도구는 "누가 실행하고 누가 책임지는가"를 바꿉니다. 비용과 보안 검토가 함께 따라붙어야 하고, 그 검토는 35장의 세 겹(권한, 데이터 최소화, 비밀)으로 할 수 있습니다.

### E.4 도구가 많을 때 — 도구 검색과 프로그래매틱 호출

도구 검색은 도구가 수십 개일 때 이름과 설명으로 필요한 도구를 찾아 쓰는 방식입니다. 14장에서 본 도구 폭증의 해법 중 하나입니다. 모든 도구 정의를 매 요청에 싣지 않아도 되므로 토큰도 줄어듭니다.

프로그래매틱 도구 호출은 모델이 코드를 써서 여러 도구 호출을 조율하는 방식입니다. 반복문과 조건문으로 호출 순서를 정할 수 있어, 같은 정보를 세 번 부르는 구조를 한 번에 줄일 수 있습니다. 대신 코드 실행 환경의 권한과 격리를 함께 설계해야 합니다.

두 기능 모두 "도구를 어떻게 고르고 부르는가"를 바꾸지, "무엇을 물을 것인가"를 바꾸지 않습니다. 질문이 흐리면 도구를 잘 골라도 답이 흐립니다. 22장의 기준이 먼저입니다.

### E.5 묶어서 배포하는 도구 — 플러그인과 마켓플레이스

플러그인은 스킬, 서브에이전트, 훅, MCP 서버를 한 단위로 묶은 배포 형식입니다. 35장에서 `triage-pack` 하나를 만들어 보았습니다. 마켓플레이스는 그 플러그인의 목록을 제공하는 저장소이고, 동료는 마켓플레이스를 등록한 뒤 이름으로 설치합니다.

시험 범위 밖이지만 조직에서 확산을 다룰 때 중요합니다. 각자 설정을 복사하는 방식은 몇 주 안에 서로 달라지고, 달라진 설정은 아무도 비교하지 않습니다. 플러그인은 버전을 붙일 수 있어 "무엇이 바뀌었는가"를 셀 수 있게 합니다.

설치 전에 확인할 것은 셋입니다. 출처, 들어 있는 훅, 그리고 문맥 비용입니다. 플러그인이 실행하는 코드는 사용자 권한으로 돌기 때문에, 검토하지 않은 훅은 검토하지 않은 스크립트를 매 호출마다 실행하는 것과 같습니다.

### E.6 컨텍스트를 관리하는 도구 — 압축, 편집, 캐시

압축은 긴 세션의 이력을 줄여 이어 가는 기능이고, 컨텍스트 편집은 오래된 도구 결과를 걷어내는 기능입니다. 둘 다 27장과 30장의 문제를 제품 기능으로 해결하는 수단입니다. 캐시는 반복되는 접두를 재사용해 비용과 지연을 줄입니다.

세 기능은 서로 당깁니다. 35장에서 본 것처럼 압축은 접두를 바꾸므로 캐시를 깨고, 캐시는 압축이 자주 일어나면 이득이 사라집니다. 그래서 순서가 중요합니다. 변하지 않는 것을 앞에 두고, 압축한 결과를 팩트 블록으로 파일에 옮겨 접두를 안정시키십시오.

시험은 이 기능들의 존재와 목적 수준만 범위에 둡니다. 구현 상세, 캐시 지점의 배치, 압축 주기의 최적화는 범위 밖입니다. 실무에서는 로그의 캐시 토큰 칸과 문맥 사용률을 함께 보며 조정합니다.

### E.7 이 책이 다루지 않는 것

다음 주제는 이 책의 범위 밖이고, 시험 범위도 아닙니다. 필요해지면 각 제품 문서에서 시작하십시오.

| 주제 | 왜 다루지 않는가 | 시작할 곳 |
|---|---|---|
| 모델 파인튜닝·커스텀 학습 | 모델을 쓰는 일과 다른 영역 | 플랫폼 문서의 모델 항목 |
| 임베딩과 벡터 검색 구현 | 검색 도구의 내부 구현 | 검색 제품 문서 |
| Computer use | 브라우저·데스크톱 자동화는 별도 설계 | 도구 사용 문서 |
| OAuth·키 로테이션 상세 | 보안의 한 부분, 35장에서 원칙만 | 보안 문서 |
| 특정 클라우드 구성 | 환경마다 다름 | 각 클라우드 문서 |
| 토크나이저·토큰 계산 상세 | 비용 계산은 35장의 회계로 충분 | 가격 문서 |

### E.8 무엇부터 익힐까

순서를 정할 때는 **지금 만드는 시스템이 막히는 지점**부터 고르십시오. 표에 우선순위를 적어 두었습니다.

| 순서 | 도구 | 언제 필요해지는가 |
|---|---|---|
| 1 | Streaming | 사용자가 응답을 기다리는 화면을 만들 때 |
| 2 | Citations | 답변에 근거를 붙여 신뢰를 얻어야 할 때 |
| 3 | Files | 같은 큰 입력을 반복해 보낼 때 |
| 4 | Vision | 입력이 사진·스캔 문서일 때 |
| 5 | 플러그인 | 같은 설정을 여러 프로젝트에 배포할 때 |
| 6 | MCP 터널 | 사내망 서버를 외부 클라이언트와 연결할 때 |
| 7 | Managed Agents | 실행 환경 운영을 맡기고 싶을 때 |
| 8 | 도구 검색·프로그래매틱 호출 | 도구가 수십 개를 넘을 때 |

이 부록의 마지막 조언은 하나입니다. 범위 밖 도구를 배울 때도 2부의 판단은 그대로입니다. 루프가 언제 멈추는지, 실패를 어떻게 알리는지, 사람에게 언제 넘기는지가 먼저이고, 도구는 그 판단을 옮기는 수단입니다. 도구를 먼저 고르고 판단을 나중에 맞추면, 시스템은 화려하지만 설명하기 어려운 것이 됩니다.
