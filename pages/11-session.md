## 11.1 이 장에서 다루는 것

이 장을 마치면 대화를 파일로 남기고, 프로세스가 죽어도 그 자리에서 이어 달리고, 같은 지점에서 두 갈래로 나눠 볼 수 있게 됩니다. 그리고 이어 달린 세션이 며칠 전에 받은 도구 결과를 그대로 믿지 않게 만듭니다.

10장까지 우리는 일을 나누고 실패를 가두는 법을 배웠습니다. 남은 문제는 대화의 수명입니다. 지금까지 만든 루프는 프로세스가 끝나면 모든 것을 잊습니다. 고객이 "아까 말한 그 주문"이라고 하면, 시스템은 처음 보는 말을 듣습니다.

이 장의 결과물은 `work/ch11-session/session.py`입니다. 세션을 저장하고 불러오고 복사하는 저장소, 단계마다 체크포인트를 남기는 루프, 그리고 오래된 도구 결과를 다시 조회하는 함수가 들어 있습니다. 실행 로그를 11.3부터 11.6까지의 절에 실었습니다.

이 장이 어려운 이유는 코드가 아니라 상태입니다. 지금까지는 한 번 실행하고 끝나는 프로그램을 다뤘는데, 이제는 실행과 실행 사이를 다룹니다. 그 사이에 무엇이 바뀌었는지를 우리가 직접 관리해야 합니다. 관리하지 않으면, 이어 달린 시스템은 자신 있게 틀린 답을 합니다.

시험의 관점에서는 "어디서 다시 시작할 것인가"와 "같은 지점에서 다른 선택을 어떻게 시험할 것인가"를 묻습니다. 답의 후보로 자주 나오는 것이 전체 재실행, 대화 되살리기, 도구 결과 주입입니다. 이 장을 읽고 나면 세 후보의 차이와 비용을 설명할 수 있게 됩니다.

## 11.2 세션이란 무엇인가

세션은 한 작업의 대화 기록입니다. 무엇을 물었고, 어떤 도구를 불렀고, 무엇이 돌아왔고, 모델이 무엇이라고 답했는지가 순서대로 들어 있습니다. 4장에서 본 메시지 목록이 곧 세션입니다.

게임의 저장 지점과 비슷합니다. 세이브가 있으면 보스를 다시 잡지 않아도 되고, 여러 세이브가 있으면 다른 선택을 시험해 볼 수 있습니다. 이 비유가 맞는 곳은 "상태를 남기면 이어서 할 수 있다"입니다. 깨지는 곳은 세계입니다. 게임은 세계 전체를 저장하지만, 세션은 대화만 저장합니다. 도구가 바깥에서 바꾼 것(주문 상태, 발송 여부)은 저장되지 않습니다.

이 차이가 이 장의 후반부를 만듭니다. 대화는 그대로인데 바깥 상태는 바뀌었을 수 있으므로, 이어 달릴 때는 "이 결과가 언제 것인가"를 물어야 합니다.

세션을 "대화의 사본"으로 이해하면 많은 결정이 쉬워집니다. 사본이므로 원본을 건드리지 않고 복사할 수 있고, 여러 사본을 만들 수 있고, 필요 없으면 지울 수 있습니다. 반대로 사본이므로 바깥 세계와는 연결되어 있지 않습니다. 이 두 문장이 재개와 포크의 모든 규칙을 담고 있습니다. 사본이라는 말을 기억하면, 포크가 왜 파일을 되돌리지 못하는지도 자연스럽게 이해됩니다.

대화가 길 때 재개가 더 어려운 이유도 여기 있습니다. 길어진 대화에는 오래된 사실이 많이 섞여 있고, 그 사실이 언제 것인지가 고르게 분포하지 않습니다. 앞부분은 모두 오래되었고, 뒷부분은 최근입니다. 사람이 읽으면 순서로 알 수 있지만, 시스템은 시각을 따로 봐야 합니다.

세션을 저장하는 이유는 세 가지입니다. 첫째, 이어 달리기입니다. 둘째, 감사입니다. 무엇을 근거로 답했는지 나중에 확인할 수 있습니다. 셋째, 평가입니다. 실제 대화를 모아 두면 시험지와 회귀 테스트의 재료가 됩니다.

세 가지 중 어느 것을 목적으로 하느냐에 따라 저장하는 내용이 달라집니다. 이어 달리기가 목적이면 짝이 맞는 이력이 중요하고, 감사가 목적이면 응답 원문과 도구 결과가 중요하며, 평가가 목적이면 입력과 최종 답이 중요합니다. 세 목적을 다 만족하려면 결국 원문을 그대로 저장하는 것이 답입니다. 가공한 저장은 어느 목적에도 반만 맞습니다. 세 목적을 동시에 노린다면 저장은 원문, 조회는 목적별로 나누는 편이 낫습니다.

## 11.3 무엇을 저장할 것인가

저장할 것은 네 가지입니다. 세션 식별자, 메시지 목록, 지금까지의 단계 수, 그리고 각 도구 결과를 받은 시각입니다. 이 넷이면 이어 달릴 수 있고, 신선도도 판단할 수 있습니다.

이 블록이 하는 일은 세션을 파일 하나로 저장하고 불러오는 저장소입니다.

```python
class SessionStore:
    def __init__(self, root):
        self.root = Path(root)
        self.root.mkdir(parents=True, exist_ok=True)

    def save(self, session):
        self.path(session["session_id"]).write_text(
            json.dumps(session, ensure_ascii=False, indent=1), encoding="utf-8")

    def load(self, session_id):
        return json.loads(self.path(session_id).read_text(encoding="utf-8"))
```

여기서 확인할 것: 세션 하나가 파일 하나입니다. 이 단순한 결정이 재개와 포크를 쉽게 만듭니다. 복사하면 갈래가 되고, 읽으면 이어 달릴 수 있습니다.

파일 이름은 식별자로 쓰고, 사람이 읽을 이름은 따로 둡니다. 식별자는 바뀌지 않아야 하고, 사람이 붙인 이름은 바뀔 수 있습니다. 둘을 섞으면 이름을 바꿀 때 참조가 깨집니다.

식별자는 짧게 만들되 충돌하지 않아야 합니다. 이 장은 무작위 8자리를 씁니다. 실제 시스템에서는 사용자 ID와 시작 시각을 조합하는 방식도 흔합니다. 어느 쪽이든 "이 ID로 어느 세션인지 찾을 수 있는가"와 "남의 세션과 겹치지 않는가" 두 가지만 만족하면 됩니다.

메시지는 가공하지 말고 그대로 저장하십시오. 4장에서 본 것처럼 응답은 블록 목록이고, 블록에는 서명이 붙은 생각 블록이 섞일 수 있습니다. 요약하거나 문자열로 바꿔 저장하면 그 구조가 사라지고, 이어 달릴 때 요청이 거부됩니다.

저장 형식도 정해야 합니다. 이 장은 JSON 파일 하나를 씁니다. 대화가 길어지면 파일이 커지지만, 사람이 열어 볼 수 있다는 장점이 있습니다. 운영에서는 데이터베이스에 넣는 경우가 많고, 그때는 메시지를 한 줄짜리 레코드로 나눠 저장합니다. 어느 쪽이든 "한 세션의 이력을 순서대로 재구성할 수 있는가"가 기준입니다.

저장 시점은 **도구 결과를 받은 직후**가 가장 좋습니다. 그 시점의 이력은 짝이 맞고, 다음 요청을 그대로 보낼 수 있습니다. 모델 응답을 받은 직후에 저장하면, 도구 결과가 아직 없어 짝이 맞지 않는 상태가 저장됩니다.

저장은 반복문 안에서 매 단계 일어나야 합니다. 마지막에 한 번 저장하면, 중간에 죽었을 때 아무것도 남지 않습니다. 저장 빈도가 높으면 디스크를 쓰는 비용이 들지만, 그 비용은 다시 계산하는 비용보다 작습니다.

저장이 실패했을 때의 처리도 정하십시오. 디스크가 가득 찼거나 권한이 없으면 저장이 실패합니다. 이때 루프를 멈출지, 계속할지를 정해야 합니다. 감사가 필요한 업무라면 저장 실패는 치명적이므로 멈추는 편이 낫습니다. 반대로 일회성 분석이라면 경고만 남기고 계속해도 됩니다.

세션 파일의 크기도 관리 대상입니다. 긴 대화는 파일 하나가 수 메가바이트가 되고, 읽고 쓰는 시간이 늘어납니다. 일정 크기를 넘으면 오래된 도구 결과를 걷어내는 규칙을 두십시오. 이때도 받은 시각을 남겨 두면, 무엇을 걷어내도 되는지 판단할 수 있습니다.

```text
세션 ID: s-fa53adbd / status: interrupted
저장된 파일: s-fa53adbd.json
메시지 수: 3 / 도구 결과 시각: ['2026-11-24T09:00:00']
```

여기서 확인할 것: 한 단계만 돌리고 멈췄는데 메시지가 셋입니다. 사용자 발언, 모델의 도구 요청, 도구 결과입니다. 짝이 맞는 상태로 저장되었습니다. 이 상태에서 다음 요청을 보내면, 모델은 도구 결과를 이미 받은 것으로 읽습니다.

## 11.4 재개 — 이어 달리기

재개는 저장된 세션을 불러와 다음 요청을 보내는 일입니다. 새 요청에는 이전 대화가 전부 들어 있으므로, 모델은 맥락을 이어서 답합니다. 우리 코드는 새로 시작하는 것과 같은 함수를 씁니다.

이 블록이 하는 일은 불러온 세션에 남은 대본을 이어 붙이는 것입니다.

```python
loaded = store.load(sid)
result = run(ScriptedTransport(script("part2")), loaded, store, now, max_steps=4)
```

여기서 확인할 것: `run`이 새 세션을 만들지 않고 받은 세션을 이어 갑니다. 같은 함수가 두 경우를 모두 처리합니다.

```text
이어서 보낸 요청 수: 2
첫 요청 메시지 수: 3 (앞 단계의 user·assistant·user가 이미 들어 있다)
답변: A-1042는 배송 중이고, 고객님은 일반 등급으로 이번 건은 전액 환불이 가능합니다.
```

여기서 확인할 것: 첫 요청에 이미 메시지 세 개가 들어 있습니다. 앞에서 지불한 토큰을 다시 계산하지 않고, 그 결과를 그대로 이어 쓴다는 뜻입니다. 재개의 이득은 여기서 나옵니다. 같은 조회를 다시 하지 않아도 됩니다.

Agent SDK에서는 이 일을 옵션 두 개로 나눕니다. `resume`은 세션 ID를 지정해 그 세션으로 돌아가고, `continue`는 현재 디렉터리의 가장 최근 세션을 이어 갑니다. ID를 직접 관리하려면 결과 메시지의 `session_id`를 읽어 저장합니다. 문서에 따르면 이 값은 성공과 실패 모두에 들어 있습니다.

두 옵션의 차이는 "무엇을 이어 갈지 내가 아는가"입니다. 사용자마다 세션이 하나씩 있는 구조라면 ID를 저장하고 `resume`을 씁니다. 한 사람이 한 번에 한 대화만 하는 구조라면 `continue`로 충분합니다. 여러 사용자가 한 서버를 쓰는 구조에서 `continue`를 쓰면, 다른 사람의 최근 세션을 이어 갈 수 있습니다.

SDK 문서는 재개의 쓰임도 세 가지로 정리합니다. 완료된 작업에 이어서 후속 요청을 할 때, 상한에 걸려 멈춘 실행을 더 큰 상한으로 이어 갈 때, 프로세스가 재시작된 뒤 대화를 되살릴 때입니다. 세 번째가 이 장의 주된 경우입니다.

재개할 때 조심할 점이 있습니다. 이어 가는 요청은 "새 작업"이 아니라 "하던 일의 계속"으로 읽혀야 합니다. 그래서 첫 문장에 무엇을 이어야 하는지 적는 편이 좋습니다. "아까 확인한 주문의 환불을 진행해 주세요"처럼 앞의 결과를 가리키면, 모델이 그 결과를 다시 찾습니다.

재개의 비용도 생각해야 합니다. 이어 가는 요청에는 이전 대화가 전부 실리므로, 첫 요청부터 입력이 큽니다. 세 단계짜리 작업을 세 번에 나눠 하면, 마지막 요청은 앞의 두 단계를 모두 포함합니다. 재개는 계산을 아끼는 장치이지, 토큰을 아끼는 장치가 아닙니다. 그러니 세션을 잘게 나누면 토큰은 오히려 늘어납니다.

## 11.5 포크 — 같은 지점에서 갈라지기

포크는 저장된 세션을 복사해 새 세션을 만드는 일입니다. 원본은 그대로 두고, 복사본에서 다른 선택을 시험합니다. 고객에게 두 가지 안을 비교해 보여 주거나, 두 모델의 답을 같은 조건에서 비교할 때 씁니다.

이 블록이 하는 일은 세션을 복사하고 새 식별자를 붙이는 것입니다. 원본과의 연결은 `parent_id`로 남깁니다.

```python
def fork(self, session_id, note=""):
    source = self.load(session_id)
    child = json.loads(json.dumps(source))
    child["session_id"] = "s-" + uuid.uuid4().hex[:8]
    child["parent_id"] = session_id
    child["note"] = note
    self.save(child)
    return child
```

여기서 확인할 것: 복사본은 새 ID를 받고, 원본 ID는 그대로입니다. `parent_id`가 있으면 나중에 어느 세션에서 갈라졌는지 추적할 수 있습니다.

```text
원본: s-fa53adbd / 포크 A: s-45285d22 / 포크 B: s-a3fce3c4
포크의 parent_id: s-fa53adbd s-fa53adbd
갈래 A 답변: 환불을 접수했습니다.
갈래 B 답변: 환불 대신 배송 지연 보상으로 안내하고 상담원에게 넘겼습니다.
원본 파일 답변: A-1042는 배송 중이고, 고객님은 일반 등급으로 이번 건은 전액 환불이 가능합니다.
남은 세션 파일: ['s-45285d22', 's-fa53adbd', 's-a3fce3c4']
```

여기서 확인할 것: 같은 지점에서 두 개의 다른 답이 나왔고, 원본은 그대로 남았습니다. 세 파일이 각각 독립적으로 이어 달릴 수 있습니다. 식별자는 실행마다 달라지므로, 직접 돌렸을 때는 다른 값이 나옵니다.

Agent SDK에서는 `resume`과 `fork_session`을 함께 씁니다. 문서에 따르면 포크는 새 세션 ID를 받고, 원본의 ID와 이력은 바뀌지 않습니다. 여기서 중요한 단서가 하나 있습니다. **포크는 대화를 가르지 파일 시스템을 가르지 않습니다.** 포크된 에이전트가 파일을 고치면 그 변경은 실제로 남고, 같은 디렉터리의 다른 세션도 봅니다. 파일까지 되돌리려면 별도의 체크포인트 기능이 필요합니다.

포크는 평가에서 특히 유용합니다. 같은 지점에서 모델만 바꿔 두 갈래를 만들면, 답의 차이가 모델 때문인지 프롬프트 때문인지 가를 수 있습니다. 이 비교를 하려면 포크 시점의 이력이 같아야 하므로, 포크를 만들 때 원본을 건드리지 않는 것이 중요합니다.

포크를 남발하면 세션이 빠르게 늘어납니다. 한 번의 탐색에 갈래 셋을 만들면 세 파일이 생기고, 그것이 쌓이면 저장 공간과 검색 시간이 늘어납니다. 탐색이 끝난 갈래는 결과만 남기고 지우는 규칙을 두십시오. 남길 것은 최종 답과 그 근거이지, 중간 대화 전부가 아닙니다.

포크의 식별자를 사람에게 보여 줄 때는 주의하십시오. 세션 ID는 그 자체로 접근 권한이 될 수 있습니다. 화면에 보여 줄 필요가 있으면 짧은 별칭을 따로 만들고, 실제 ID는 서버에만 두십시오.

## 11.6 오래된 결과 — 재개가 만드는 새로운 위험

이어 달리기의 가장 큰 위험은 오래된 사실입니다. 세션은 대화를 저장하지만, 바깥 상태는 저장하지 않습니다. 사흘 전에 "배송 중"이던 주문이 오늘 도착했을 수 있습니다.

이 장은 도구 결과마다 받은 시각을 남기고, 24시간이 지난 결과를 다시 조회합니다. 결과의 성격에 따라 기간은 달라져야 합니다. 배송 상태는 하루면 바뀌고, 환불 이력은 한 달이 지나도 그대로입니다.

기간을 결과의 종류별로 정해 두면 관리가 쉽습니다. 주문 상태는 24시간, 고객 등급은 30일, 정책 문서는 90일처럼 표로 둡니다. 이 표가 없으면 모든 결과를 같은 기준으로 판단하게 되고, 그러면 어느 쪽으로든 틀립니다.

재조회한 값이 이전과 다를 때는 그 사실을 답에 반영하십시오. "확인해 보니 상태가 배송 완료로 바뀌었습니다"라고 말하는 편이, 조용히 새 값만 쓰는 것보다 낫습니다. 고객은 왜 답이 달라졌는지 이해할 수 있습니다.

재조회에도 상한이 필요합니다. 오래된 결과가 스무 개면 스무 번을 다시 부르게 되고, 그 비용이 원래 작업보다 커집니다. 그래서 재개할 때는 "이 답에 실제로 쓰일 결과"만 다시 확인합니다. 쓰이지 않을 결과를 미리 새로 받는 것은 낭비입니다.

```text
오래된 결과: [('lookup_order', '2026-11-24T09:00:00'), ('get_customer', '2026-11-24T09:00:00')]
재조회: [('lookup_order', True), ('get_customer', False)] → 상태가 바뀐 건은 true
```

여기서 확인할 것: 두 결과 중 하나는 값이 바뀌었고, 하나는 그대로입니다. 바뀐 쪽만 이력에서 교체하고, 그 사실을 기록합니다. 24시간이 지났다고 무조건 다시 부르면 비용이 늘고, 다시 부르지 않으면 틀린 답을 합니다.

시각이 없으면 판단할 수 없습니다. 시각을 지운 세션으로 같은 함수를 부르면 예외가 납니다.

```text
KeyError: 'fetched_at' → 결과에 시각을 남기지 않으면 신선도를 판단할 수 없다
```

여기서 확인할 것: 이 예외는 일부러 만든 것입니다. 시각이 없는 세션을 만나면, 조용히 넘어가지 말고 다시 조회하는 편이 안전합니다. 모르면 새로 받는 것이 원칙입니다.

## 11.7 세션의 위험 네 가지

첫째, **동시 재개**입니다. 두 프로세스가 같은 세션을 동시에 이어 가면, 같은 도구를 두 번 실행합니다. 쓰기 도구라면 두 번의 환불입니다. 세션에 잠금을 걸거나, 한 세션은 한 번에 한 실행만 허용하는 규칙이 필요합니다.

잠금은 파일 잠금이나 데이터베이스의 조건부 갱신으로 구현합니다. 핵심은 "이 세션이 지금 실행 중인가"를 저장하는 것입니다. 실행이 끝나면 풀고, 비정상 종료로 남은 잠금은 만료 시간으로 정리합니다. 잠금이 없으면, 재시도가 두 번 실행되는 사고가 가장 흔하게 납니다.

둘째, **비밀 값의 저장**입니다. 대화에는 도구 결과가 그대로 들어 있고, 그 안에 토큰이나 카드 번호가 섞일 수 있습니다. 저장 전에 마스킹하는 단계를 두십시오. 파일 권한도 함께 확인해야 합니다.

셋째, **보관 기간**입니다. 고객 대화를 무기한 저장하면 개인정보 저장소가 하나 늘어납니다. 보관 기간과 삭제 절차를 정하고, 그 기간이 지난 세션은 지웁니다. 감사 목적으로 남겨야 한다면, 원문 대신 필요한 필드만 남기는 방법도 있습니다.

넷째, **세션 식별자의 노출**입니다. 세션 ID를 알면 그 대화를 이어 갈 수 있습니다. 외부에 노출되는 링크에 세션 ID를 넣지 마십시오. 필요하면 짧은 수명의 토큰으로 한 번만 접근하게 합니다.

세 번째와 네 번째는 법과 직결되기도 합니다. 고객 대화에는 이름과 연락처가 들어 있고, 그 대화를 지우지 않고 보관하면 삭제 요청에 응하기 어려워집니다. 세션을 만들 때부터 "이 대화를 언제 지울 것인가"를 정해 두십시오.

## 11.8 흔한 실패 다섯 가지

이 실패들은 대부분 "이어 달리기는 되면 된다"는 생각에서 생깁니다. 되기만 하면 되는 일이 아니라, 이어 달린 결과가 여전히 사실에 맞는지까지 봐야 하는 일입니다.

첫째, **응답만 저장하는 것**입니다. 모델의 답변 문장만 남기면, 블록 구조와 도구 호출 기록이 사라집니다. 이어 달릴 때 짝이 맞지 않아 요청이 거부됩니다.

둘째, **도구 결과의 시각을 빼는 것**입니다. 11.6의 예외처럼, 시각이 없으면 신선도를 판단할 수 없습니다. 시각은 저장할 때 반드시 함께 넣으십시오.

저장된 세션을 "믿을 수 있는 기록"으로 다루는 것도 조심해야 합니다. 세션 파일은 우리가 만든 것이지만, 외부에서 온 세션을 이어 받는 구조라면 그 내용이 조작될 수 있습니다. 도구 결과를 그대로 신뢰하지 말고, 중요한 값은 다시 조회하십시오. 신뢰의 기준은 저장 위치가 아니라 조회 시각입니다.

셋째, **포크가 파일까지 되돌린다고 믿는 것**입니다. 문서가 명시하듯 포크는 대화만 가릅니다. 파일을 되돌리려면 별도의 체크포인트가 필요합니다. 이 차이를 모르면, 두 갈래를 비교했는데 두 갈래의 파일 변경이 섞여 있어 비교가 무의미해집니다.

넷째, **재개한 세션에 새 시스템 프롬프트를 넣는 것**입니다. 대화는 이전 지시로 시작했는데 중간에 지시가 바뀌면, 모델은 어느 쪽을 따라야 할지 흔들립니다. 지시를 바꿔야 한다면 새 세션으로 시작하십시오.

다섯째, **세션을 무한히 키우는 것**입니다. 대화가 길어지면 매 요청의 입력이 커지고, 3장의 컨텍스트 부패가 나타납니다. 일정 길이를 넘으면 요약하거나, 새 세션으로 나누십시오. 27장이 그 방법을 다룹니다.

이 다섯 중 첫째와 둘째는 코드를 조금 고치면 막을 수 있고, 나머지 셋은 운영 규칙이 필요합니다. 코드로 막을 수 있는 것을 먼저 막고, 나머지는 문서로 정해 두십시오. 세션은 한 번 잘못 저장하면 지우기 어려우므로, 저장 전에 막는 편이 낫습니다.

## 11.9 실습 — 중단하고, 이어 달리고, 갈라 보기

1. `work/ch11-session/`에서 `python3 verify.py`를 실행합니다.
확인: 다섯 시나리오가 출력되고 "모든 검증 통과"로 끝납니다.
2. `max_steps=1`을 `2`로 바꿔 실행합니다.
확인: 중단 시점의 메시지 수가 늘고, 재개할 때 보내는 요청 수가 줄어듭니다.
3. `STALE_HOURS`를 48로 바꿔 실행합니다.
확인: 30시간 지난 결과는 오래된 것으로 잡히지 않아 재조회가 일어나지 않습니다.
4. `refresh_stale`을 호출하지 않게 바꿉니다.
확인: 재조회 로그가 사라지고, 이력에는 옛 상태가 그대로 남습니다.

4번을 실행하면, 조용한 실패가 어떻게 생기는지 보게 됩니다. 오류는 없고, 답도 나오지만, 그 답은 사흘 전 사실에 근거합니다. 이런 실패가 가장 찾기 어렵습니다.

## 11.10 검증한 것과 하지 못한 것

검증한 것은 저장·재개·포크·신선도입니다. 한 단계만 돌리고 멈췄을 때 세션이 남는 것, 새 프로세스에서 이어 달릴 때 이력이 이미 들어 있는 것, 포크가 새 ID를 받고 원본을 바꾸지 않는 것, 24시간 지난 결과를 찾아 다시 조회하는 것, 시각이 없으면 예외가 나는 것을 확인했습니다.

하지 못한 것은 SDK의 실제 세션 저장소입니다. 이 환경에는 Agent SDK가 없어 `resume`·`fork_session`을 실제로 돌리지 못했고, 옵션 이름과 동작은 공식 문서로 확인했습니다. 문서에 따르면 세션 파일은 사용자 홈의 프로젝트 폴더 아래에 JSONL로 쌓이고, 다른 기기에서 이어 가려면 저장소 어댑터를 따로 붙여야 합니다. 이 장의 파일 저장소는 그 구조를 단순화한 것입니다.

동시 재개도 실제로 재현하지 못했습니다. 두 프로세스가 같은 파일을 동시에 쓰면 마지막 쓰기가 이기고, 그 사이에 실행된 도구 호출은 사라집니다. 이 문제는 실제 운영에서만 드러나므로, 세션을 설계할 때 잠금을 미리 넣어 두는 편이 안전합니다.

이 장의 검증 범위를 한 줄로 줄이면 이렇습니다. "한 프로세스 안에서 저장·재개·포크·신선도 판단이 동작하는 것을 확인했고, 여러 프로세스와 SDK 저장소는 문서로만 확인했다." 이 구분을 기억하면, 운영으로 옮길 때 무엇을 다시 시험해야 하는지 알 수 있습니다.

## 11.11 이 개념이 프로덕션에서 커지는 지점

세션은 9장의 승인 대기와 만납니다. 승인을 기다리는 루프는 세션을 저장하고 기다렸다가, 승인이 오면 그 지점에서 다시 시작합니다. 저장이 없으면 승인 대기 중에 프로세스가 죽었을 때 처음부터 다시 해야 합니다.

33장의 평가에서는 세션을 시험 재료로 씁니다. 실제 대화를 저장해 두면, 모델이나 프롬프트를 바꿨을 때 같은 입력으로 다시 돌려 비교할 수 있습니다. 이때 포크가 유용합니다. 같은 지점에서 두 설정으로 갈라 놓으면, 차이가 어디서 생겼는지 정확히 볼 수 있습니다.

Part II를 마치며 한 번 정리해 보겠습니다. 우리는 루프를 수명주기로 다듬고(6장), 일을 나눴고(7장), 넘기는 방식과 동시성을 정했고(8장), 코드로 문을 세웠고(9장), 크기를 정했고(10장), 대화의 수명을 다뤘습니다(11장). 여섯 장이 만든 것은 결국 하나의 질문에 대한 답입니다. "이 일을 누가, 무엇을 받아, 어디서 멈추고, 어떻게 이어 가는가." 다음 파트의 도구 설계는 이 질문에 한 겹을 더합니다.

## 11.12 이 장의 체크리스트

이 장의 항목은 앞의 네 장보다 많습니다. 세션은 한 번 잘못 만들면 고치기 어려운 결정이 많기 때문입니다. 특히 저장 시점과 신선도 기준은 나중에 바꾸기 어려우니, 처음에 정확히 잡으십시오. 열 항목 중 여섯 개에 답하지 못하면 11.3부터 다시 읽으십시오.

- [ ] 세션이 대화만 저장하고 바깥 상태는 저장하지 않음을 안다.
- [ ] 세션 ID·메시지·단계·결과 시각을 저장한다.
- [ ] 메시지를 가공하지 않고 그대로 저장한다.
- [ ] 도구 결과 직후에 체크포인트를 남긴다.
- [ ] 재개는 새 요청에 이력을 그대로 싣는 일임을 안다.
- [ ] `resume`과 `continue`의 차이를 안다.
- [ ] 포크가 새 세션 ID를 받고 원본을 바꾸지 않음을 안다.
- [ ] 포크가 파일 시스템을 가르지 않음을 안다.
- [ ] 오래된 도구 결과를 찾아 다시 조회한다.
- [ ] 같은 세션을 동시에 이어 가지 않게 막았다.

이 장으로 Part II가 끝납니다. 다음 파트에서는 도구의 설명과 오류를 설계합니다. 지금까지 만든 구조 위에, 도구를 더 정확히 고르게 만드는 방법이 얹힙니다. 구조가 튼튼해도 도구가 엉뚱하게 선택되면 결과는 틀리고, 그 문제는 다음 파트에서 다룹니다. 좋은 구조가 좋은 선택을 보장하지는 않습니다.
