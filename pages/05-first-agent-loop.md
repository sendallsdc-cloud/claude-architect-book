## 05.1 이 장에서 다루는 것

이 장을 마치면 도구를 스스로 부르는 **30줄짜리 루프** 하나를 갖게 됩니다. 그리고 그 루프를 일부러 네 가지로 망가뜨려 보고, 왜 망가지는지 확인한 뒤 고칩니다. 마지막에는 여섯 가지 상황에서 루프가 어떻게 동작하는지 실행 로그로 확인합니다.

4장에서 왕복 한 번을 배웠습니다. 질문을 보내고, `tool_use`가 오면 도구를 실행하고, 결과를 돌려주고, 다시 답을 받았습니다. 이 장은 그 왕복을 `while` 안에 넣습니다. 반복에는 반드시 끝나는 조건이 필요하고, 그 조건을 잘못 적는 것이 초보의 첫 번째 실패입니다.

코드는 다섯 블록입니다. 초안, 고친 루프의 본체, 도구 실행부, 검증 로그, 실제 호출 전환입니다. 각 블록 앞에 무엇을 하는지 한 줄로 적었으니, 코드를 읽기 전에 그 줄부터 보십시오.

읽는 순서를 하나 권한다면, 05.3의 초안과 05.5의 고친 본체를 나란히 놓고 다른 점만 세어 보십시오. 달라진 곳이 네 군데뿐이고, 그 네 군데가 이 장의 전부입니다. 종료를 텍스트로 판단하던 것을 `stop_reason`으로 바꾸었고, 잘림을 예외로 분리했고, 모르는 값을 거부하게 했고, 도구 실패를 결과로 돌려주게 했습니다.

이 장의 예제는 워크스페이스의 `work/ch05-agent-loop/`에 있습니다. 본문에 다 싣지 않은 파일이 있으므로, 직접 돌려 보려면 그 폴더를 통째로 쓰십시오. API 키 없이 돌아갑니다.

5장은 1부의 마지막 장이자 이 책의 분기점입니다. 여기까지는 "무엇을 쓰는가"를 배웠고, 여기부터는 "어떻게 동작하게 만드는가"를 다룹니다. 이 장의 루프는 앞으로 나올 모든 에이전트의 뼈대입니다.

## 05.2 루프는 "끝났다"를 읽는 일이다

에이전트 루프의 본질은 반복이 아니라 **종료 판단**입니다. 모델에게 일을 시키고, 결과를 받아 다시 물어보는 일은 쉽습니다. 어려운 것은 "이제 그만 물어봐도 되는가"를 아는 일입니다.

심부름과 비슷합니다. 아이에게 "우유 사 오고, 없으면 두유 사 와"라고 시키면, 아이는 다녀와서 "우유는 없었고 두유를 샀어"라고 말합니다. 부모는 그 말을 듣고 "그럼 이제 됐다"고 판단합니다. 루프에서 모델이 하는 일은 아이가 다녀온 보고이고, 종료 판단은 부모의 몫입니다. 이 비유가 맞는 곳은 "보고와 판단이 분리되어 있다"는 점입니다. 깨지는 곳은 숫자입니다. 아이는 한 번에 한 가지를 하지만, 모델은 한 응답에서 도구 세 개를 동시에 시킬 수 있습니다.

그래서 루프를 짤 때 가장 먼저 정할 것은 "무엇을 보면 끝인가"입니다. 4장의 답은 하나였습니다. `stop_reason`이 `end_turn`이면 끝입니다. 다른 값을 어떻게 처리할지가 나머지 설계입니다.

루프는 세 부분으로 나뉩니다. 요청을 보내는 부분, 도구를 실행하는 부분, 그리고 끝났는지 판단하는 부분입니다. 초보는 두 번째에 시간을 쓰고 세 번째를 한 줄로 처리합니다. 그러나 운영에서 사고를 만드는 것은 세 번째입니다. 잘못된 종료 판단은 무한 반복이 되거나, 반대로 일을 마치지 않고 끝난 것처럼 보입니다.

반복 횟수의 상한도 여기에 속합니다. `while True`를 쓰지 않고 `for step in range(1, max_steps + 1)`을 쓰는 이유는, 어떤 조건이 꼬여도 유한 번 안에 끝나게 하기 위해서입니다. 상한은 "이만큼까지는 정상"이라는 선언이고, 상한에 닿았다면 정상이 아니라는 신호입니다.

루프를 쓰지 않고 한 번의 요청으로 끝내는 방법도 있습니다. 모델이 모든 도구 결과를 미리 갖고 있다면 한 번으로 끝납니다. 그러나 주문 번호를 모르는 상태에서 주문을 조회할 수는 없습니다. 첫 응답을 받아야 다음 조회가 가능하고, 그 조회 결과를 받아야 환불 여부를 판단할 수 있습니다. 의존하는 단계가 있으면 루프가 필요합니다.

## 05.3 초안 — 30줄짜리 루프

먼저 일부러 틀린 초안을 봅니다. 이 블록이 하는 일은 모델을 부르고, 텍스트가 있으면 답이 끝난 것으로 보고 반환하는 루프입니다.

틀린 코드를 먼저 보는 이유는, 올바른 코드만 보면 왜 그렇게 썼는지가 보이지 않기 때문입니다. 오류를 먼저 보고 고치면 그 오류가 기억에 남습니다. 실제로 초보 코드의 대부분은 이 초안과 비슷한 모양입니다.

```python
def run(transport, user_text: str, max_steps: int = 10) -> str:
    messages = [{"role": "user", "content": user_text}]
    for _ in range(max_steps):
        response = transport.create(
            model=MODEL, max_tokens=1024, system=SYSTEM, tools=TOOLS, messages=messages
        )
        # 실패 지점 1: 텍스트가 조금이라도 있으면 답이 끝났다고 본다.
        text = "".join(b["text"] for b in response["content"] if b["type"] == "text")
        if text:
            return text

        messages.append({"role": "assistant", "content": response["content"]})
        results = []
        for block in response["content"]:
            if block["type"] != "tool_use":
                continue
            # 실패 지점 2: 없는 도구 이름이면 예외로 루프가 죽는다.
            value = REGISTRY[block["name"]](**block["input"])
            results.append({"type": "tool_result", "tool_use_id": block["id"],
                            "content": as_text(value)})
        messages.append({"role": "user", "content": results})
    return "(단계 상한 초과)"
```

여기서 확인할 것: 열한 줄짜리 루프가 사실상 4장의 왕복을 반복합니다. 눈여겨볼 곳은 `if text:` 한 줄입니다. 여기가 첫 번째 실패 지점입니다.

코드에 `transport`라는 낯선 이름이 나옵니다. 이것은 모델을 부르는 부분을 한 겹 감싼 객체입니다. 대본을 재생하는 버전과 실제 API를 부르는 버전이 같은 인터페이스를 갖습니다. 이렇게 해 두면 루프 코드는 바꾸지 않고 호출 대상만 바꿀 수 있습니다. 테스트에서 흔히 쓰는 방식입니다.

`TOOLS`와 `SYSTEM`은 4장에서 본 도구 정의와 지시문입니다. `REGISTRY`는 도구 이름을 실제 함수에 연결한 딕셔너리입니다. 세 가지가 준비되어 있으면 루프는 짧아집니다.

초안이 짧은 것은 기능이 적어서가 아니라 검사가 없어서입니다. 검사를 넣으면 줄이 두 배가 됩니다. 그 두 배가 운영에서 사고를 막는 부분이므로, "짧은 코드"를 목표로 삼지 마십시오. 목표는 "예상한 상황에서 멈추는 코드"입니다.

이 초안을 정상 대본으로 돌리면 이렇게 됩니다.

```text
반환값: 주문 내역부터 확인하겠습니다.
모델 호출 횟수: 1 (도구는 실행되지 않음)
```

여기서 확인할 것: 사용자는 "주문 내역부터 확인하겠습니다"라는 말만 듣고 끝났습니다. 배송 상태도, 운송장 번호도, 환불 가능 여부도 없습니다. 도구는 한 번도 실행되지 않았습니다.

## 05.4 왜 인사말에서 멈췄나

모델의 첫 응답에는 텍스트와 `tool_use`가 함께 있었습니다. "주문 내역부터 확인하겠습니다"라는 문장과 "lookup_order를 불러라"라는 요청이 한 응답에 들어 있습니다. 초안은 텍스트를 보고 반환했으므로, 도구 요청은 버려졌습니다.

이 실패는 초안이 게을러서가 아닙니다. "사람에게 보이는 문장이 있으면 대화가 끝난 것"이라는 그럴듯한 가정이 틀렸기 때문입니다. 모델은 일을 시작하기 전에 무엇을 할지 말하는 습관이 있습니다. 그 인사말이 종료 신호로 오해됩니다.

왜 모델이 인사말을 먼저 할까요? 긴 작업에서 사용자에게 진행을 알리는 편이 자연스럽기 때문입니다. 이 습관은 장점이기도 합니다. 사용자는 멈춘 것이 아니라 일하는 중임을 압니다. 문제는 그 장점이 코드의 종료 판단과 충돌한다는 점입니다.

문자열을 검색하는 우회도 생각할 수 있습니다. "확인하겠습니다"가 있으면 계속, "입니다"로 끝나면 종료처럼 판단하는 방식입니다. 이 방법은 며칠은 버티지만 곧 깨집니다. 문장이 조금만 달라져도 규칙이 빗나가고, 반대 경우도 생깁니다. 규칙을 추가할수록 유지보수가 어려워집니다.

사용자 경험 면에서도 인사말은 필요합니다. 오래 걸리는 작업에서 아무 말 없이 멈춰 있는 에이전트는 고장 난 것처럼 보입니다. 그래서 모델의 습관을 없애려 하지 말고, 코드가 그 습관을 이해하게 만드십시오. 이것이 이 장이 가르치는 자세입니다.

이 함정은 시험에서도 비중 있게 다뤄집니다. "텍스트 유무나 반복 횟수로 종료를 판단하지 말고 `stop_reason`을 보라"는 것이 이 도메인의 기본 원칙입니다. 6장에서 이 원칙을 수명주기로 확장합니다.

같은 함정의 다른 얼굴도 있습니다. 텍스트가 아예 없는데 `end_turn`이 오는 경우입니다. 4장에서 본 빈 응답입니다. 이때 초안은 텍스트가 없으니 도구 실행으로 넘어가고, 실행할 도구도 없으니 빈 결과를 보내고, 결국 상한까지 돕니다. 두 경우 모두 원인은 같습니다. **내용을 보고 상태를 추측한 것**입니다.

신호등과 `stop_reason`을 비교해 봅시다. 신호등은 색이 정해져 있고, 우리는 색을 본다. `stop_reason`도 값이 정해져 있고, 우리는 값을 본다. 비유가 깨지는 곳은 개수입니다. 신호등은 세 가지지만 `stop_reason`은 일곱 가지이고, 앞으로 늘어날 수 있습니다. 그래서 "초록이 아니면 멈춘다"처럼 쓰면 안 되고, 모르는 값은 오류로 처리해야 합니다.

쉽게 말해, 종료 판단은 텍스트가 아니라 상태값으로 합니다. 텍스트는 사용자에게 보일 내용이고, 상태값은 내가 판단할 근거입니다.

## 05.5 stop_reason으로 끝을 판단하기

고친 루프의 뼈대는 이렇습니다. 이 블록이 하는 일은 `stop_reason`을 분기해 끝낼지, 도구를 실행할지, 멈추고 알릴지를 정하는 것입니다.

```python
for step in range(1, max_steps + 1):
    response = transport.create(model=MODEL, max_tokens=1024,
                                system=SYSTEM, tools=TOOLS, messages=messages)
    stop = response["stop_reason"]

    if stop == "end_turn":
        text = text_of(response["content"])
        if not text:
            raise LoopError("end_turn인데 텍스트가 비었다. 대화 이력을 확인한다.")
        return {"text": text, "steps": step, "messages": messages, "log": log}

    if stop == "max_tokens":
        raise Truncated("응답이 max_tokens에 걸려 잘렸다. 상한을 올리거나 일을 쪼갠다.")

    if stop != "tool_use":
        raise LoopError(f"처리하지 않은 stop_reason={stop}")

    messages.append({"role": "assistant", "content": response["content"]})
    results = [run_tool(b, seen, log) for b in response["content"] if b["type"] == "tool_use"]
    messages.append({"role": "user", "content": results})
```

여기서 확인할 것: `end_turn`일 때 텍스트가 비었는지 한 번 더 확인합니다. 그리고 모르는 값은 조용히 무시하지 않고 예외로 올립니다. 조용히 무시하면 루프가 도는 것처럼 보이지만 아무 일도 하지 않습니다.

`max_tokens`를 예외로 처리한 이유가 있습니다. 잘린 응답은 정상 응답처럼 보입니다. 문장이 중간에서 끊겼을 뿐, 오류가 아닙니다. 이때 그대로 사용자에게 보내면 잘린 답이 나갑니다. 초안이 실제로 그렇게 했습니다. 잘린 응답을 반환한 값은 "운송장 번호는 1234-5678-90"에서 끊겨 있었습니다.

예외를 몇 종류로 나눈 것도 설계입니다. `Truncated`는 상한을 올리면 해결되는 문제, `StepLimit`은 진행이 없다는 신호, `LoopError`는 그 밖의 예상 밖 상태입니다. 호출부는 이 셋을 다르게 처리합니다. 상한은 알림, 단계 초과는 사람 연결, 나머지는 로그와 함께 오류 보고입니다.

예외 대신 결과를 반환하는 방식도 있습니다. 루프를 라이브러리로 배포한다면 예외보다 결과 객체가 다루기 쉽습니다. 이 책이 예외를 택한 이유는 실패를 조용히 삼키지 않기 위해서입니다. 반환값으로 바꾸면 호출부가 확인하지 않고 넘어가는 경우가 생깁니다.

종료 판단을 함수로 빼 두는 것도 방법입니다. `should_continue(stop_reason)` 같은 함수를 두고, 루프는 그 함수의 답만 따르게 합니다. 종료 규칙이 바뀌면 함수만 고치면 되고, 테스트도 쉬워집니다. 루프가 길어지기 시작하면 이렇게 나누십시오.

반환값에 진행 기록을 넣은 것도 같은 이유입니다. `steps`와 `log`를 남기면 "이 문의가 왜 3단계에서 끝났는가"를 나중에 볼 수 있습니다. 기록 없는 루프는 운영에서 가장 먼저 후회하는 부분입니다.

## 05.6 도구 실행부 — 실패도 결과다

도구를 실행하는 부분은 루프에서 가장 사고가 많은 곳입니다. 이 블록이 하는 일은 도구를 이름으로 찾아 실행하고, 실패를 `tool_result`로 바꿔 돌려주는 것입니다.

```python
def run_tool(block: dict, seen: set, log: list) -> dict:
    name, args = block["name"], block["input"]
    key = (name, json.dumps(args, sort_keys=True, ensure_ascii=False))
    if key in seen:
        return _result(block["id"], "같은 인자로 이미 호출했다. 다른 인자를 쓰거나 사용자에게 알린다.", True)
    seen.add(key)
    if name not in REGISTRY:
        return _result(block["id"], f"'{name}' 도구는 없다. 쓸 수 있는 도구: lookup_order, get_customer, escalate_to_human.", True)
    try:
        value = REGISTRY[name](**args)
    except (LookupError, TypeError) as exc:
        return _result(block["id"], f"{name} 실패: {exc}", True)
    return _result(block["id"], as_text(value), False)
```

여기서 확인할 것: 세 가지 실패(중복, 없는 도구, 실행 오류)가 모두 `tool_result`로 돌아갑니다. 루프는 죽지 않습니다.

`REGISTRY`를 딕셔너리로 둔 이유는 안전 때문입니다. 문자열을 그대로 함수 이름으로 바꾸는 방식(`globals()[name]`)은 위험합니다. 모델이 예상하지 못한 이름을 보내면 그 이름의 무엇이든 실행될 수 있습니다. 딕셔너리는 허용한 이름만 통과시킵니다.

인자를 그대로 함수에 넘기는 것도 위험합니다. 이 예제는 키워드 인자로만 넣으므로 이름이 다른 인자는 `TypeError`가 나고, 그것도 오류 결과로 돌아갑니다. 실제 시스템에서는 여기에 검증을 더합니다. 금액 상한, 식별자 형식, 허용된 열람 범위를 확인하는 단계입니다. 9장의 강제 장치가 그 자리입니다.

결과의 크기도 신경 쓰십시오. 도구가 3KB짜리 JSON을 돌려주면 그 값이 대화에 그대로 쌓입니다. 필요한 필드만 골라 돌려주면 다음 요청부터 비용이 줍니다. 이 장의 `lookup_order`는 결과 전체를 돌려주지만, 32장의 `search_docs`는 본문을 빼고 식별자만 돌려줍니다.

실행 시간도 함께 다루십시오. 이 장의 도구는 메모리에서 값을 찾으므로 즉시 끝나지만, 실제 도구는 외부 API를 부르고 몇 초가 걸립니다. 오래 걸리는 도구는 루프 전체를 멈추게 합니다. 도구마다 시간 제한을 두고, 넘으면 오류 결과로 처리하는 편이 좋습니다. 이 책의 루프에는 들어 있지 않지만, 실무에 옮길 때 가장 먼저 추가할 부분입니다.

없는 도구를 불렀을 때의 로그입니다. 모델은 자기 실수를 읽고 방향을 바꿉니다.

```text
도구 실행: [('check_refund_policy', 'unknown')]
is_error: True
모델이 받은 문장: 'check_refund_policy' 도구는 없다. 쓸 수 있는 도구: lookup_ ...
최종 답변: 환불 규정을 조회하는 도구가 없어 확인이 어렵습니다. ...
```

여기서 확인할 것: 오류를 던지지 않고 문장으로 돌려주었더니 대화가 이어졌습니다. 만약 여기서 `KeyError`를 던졌다면 루프가 죽고 사용자는 아무 답도 못 받습니다.

한 가지를 구분하십시오. 도구 실행의 실패는 모델이 고칠 수 있는 실패입니다. 없는 도구를 부른 것, 인자 형식이 틀린 것은 모델이 다음 턴에 고칩니다. 반면 API 인증 실패나 네트워크 단절은 모델이 고칠 수 없습니다. 전자는 `tool_result`로, 후자는 예외로 처리해야 합니다. 13장에서 이 분류를 형식으로 만듭니다.

쉽게 말해, 도구가 실패해도 루프는 죽지 않아야 합니다. 실패도 결과로 돌려주면 모델이 다른 길을 찾습니다.

## 05.7 같은 호출이 반복될 때

루프에는 두 가지 안전장치가 필요합니다. 단계 상한과 중복 감지입니다. 단계 상한만으로는 부족합니다. 상한이 8이면 같은 호출을 8번 반복한 뒤에야 멈추고, 그동안 비용은 8번 나갑니다.

중복 감지는 같은 도구를 같은 인자로 다시 부른 경우를 잡습니다. 인자를 정렬해 키로 만들고, 이미 본 키면 결과 대신 "이미 호출했다"는 문장을 돌려줍니다. 모델은 이 문장을 읽고 다른 인자를 쓰거나 사용자에게 알립니다.

```text
도구 실행: [('lookup_order', 'ok'), ('lookup_order', 'duplicate')]
2번째 tool_result: {'type': 'tool_result', 'tool_use_id': 'toolu_03B',
 'content': '같은 인자로 이미 호출했다. 다른 인자를 쓰거나 사용자에게 알린다.', 'is_error': True}
```

여기서 확인할 것: 중복을 감지해도 루프를 멈추지 않습니다. 멈추면 모델이 다른 방법을 시도할 기회를 잃습니다. 대신 사실을 알려 주고 한 단계를 더 줍니다.

단계 상한은 마지막 방어선입니다. 8단계를 넘으면 진행이 없다고 보고 예외를 던집니다. 상한값은 작업에 따라 다르지만, 고객 문의 하나에 8단계면 충분합니다. 상한에 자주 닿는다면 상한을 올리기 전에 도구 설명을 먼저 보십시오. 모델이 헤매는 이유는 대개 설명이 모호하기 때문입니다.

중복 감지에도 한계가 있습니다. 정당하게 같은 도구를 두 번 불러야 하는 경우가 있습니다. 예를 들어 고객이 "방금 추가한 주문도 봐 줄래요"라고 하면 같은 조회를 다시 해야 합니다. 그래서 중복을 "차단"이 아니라 "경고"로 처리했습니다. 모델이 경고를 읽고도 같은 호출이 필요하다고 판단하면, 단계 상한이 최종으로 멈춥니다.

두 장치의 역할을 정리하면 이렇습니다. 중복 감지는 비용을 줄이고, 단계 상한은 사고를 막습니다. 둘 중 하나만 있으면 어느 한쪽이 무너집니다. 중복만 있으면 서로 다른 호출을 반복하며 도는 경우를 못 막고, 상한만 있으면 상한까지 비용을 쓴 뒤에 멈춥니다.

상한값을 정할 때는 정상 경로의 길이를 먼저 재십시오. 1번 시나리오에서 3단계로 끝났습니다. 여유를 두어 두 배인 6~8단계를 상한으로 잡으면 됩니다. 작업이 복잡해지면 상한도 올라가지만, 올리는 이유를 적어 두십시오.

## 05.8 여섯 시나리오 검증

워크스페이스의 `verify.py`는 여섯 가지 상황을 순서대로 돌립니다. 대본은 `fixtures/`의 JSON 파일이고, 각 파일은 4장에서 본 응답 모양 그대로입니다.

```text
== 1) 정상 경로 — 도구 2회 실행 뒤 종료 ==
단계 수: 3 / 도구 실행: [('lookup_order', 'ok'), ('get_customer', 'ok')]
2번째 요청의 메시지 수: 3
tool_result id 일치: True

== 2) 초안(loop_v1)의 실패 — 첫 턴의 인사말을 최종 답으로 반환 ==
반환값: 주문 내역부터 확인하겠습니다.

== 3) max_tokens로 잘린 응답 ==
Truncated: 응답이 max_tokens에 걸려 잘렸다. 상한을 올리거나 일을 쪼갠다.

== 4) 없는 도구를 부른 경우 — 오류를 결과로 돌려주고 계속 ==
도구 실행: [('check_refund_policy', 'unknown')]

== 5) 같은 호출 반복 — 중복을 표시하고 진행을 멈추지 않는다 ==
도구 실행: [('lookup_order', 'ok'), ('lookup_order', 'duplicate')]

== 6) 단계 상한 — 끝나지 않는 대본 ==
StepLimit: 4단계 안에 끝나지 않았다.
```

여기서 확인할 것: 1번에서 도구가 두 번 실행되고 3단계 만에 끝났습니다. 2번은 고치지 않은 초안이고, 3번부터 6번은 고친 루프의 방어 동작입니다.

1번의 "2번째 요청의 메시지 수: 3"을 눈여겨보십시오. 두 번째 요청에 user, assistant, user 세 메시지가 들어 있다는 뜻입니다. 4장에서 본 짝맞춤이 실제로 반복되고 있다는 증거입니다. "tool_result id 일치: True"도 같은 짝을 확인한 것입니다.

6번의 로그가 조금 이상하게 보일 수 있습니다. 같은 호출을 반복하는 단계마다 중복이 감지되어 4단계 만에 상한에 닿았습니다. 상한이 없었다면 이 대본은 영원히 돌았을 것입니다.

검증 범위를 분명히 밝힙니다. 이 실행은 실제 API가 아니라 대본을 재생한 것입니다. 루프의 구조, 종료 판단, 도구 실행, 오류 처리, 상한은 실행해 확인했지만, **모델이 어떤 도구를 고르는지는 확인하지 못했습니다.** 모델의 선택은 대본으로 재현할 수 없고, 실제 호출이 필요합니다. 그 부분은 12장의 도구 설명 설계와 33장의 평가로 다룹니다.

대본으로 검증하는 방식을 얕보지 마십시오. 대본은 "이런 응답이 오면 루프가 어떻게 반응하는가"를 정확히 재현합니다. 오류 처리와 종료 판단은 모델의 지능과 무관하게 결정되므로, 대본만으로도 충분히 검증됩니다. 반대로 "모델이 좋은 도구를 고르는가"는 대본으로 검증할 수 없습니다.

실제 응답을 대본으로 쓰는 방법도 있습니다. 4장의 실습에서 받은 응답을 저장해 두고, 그것을 순서대로 재생하면 된다. 실제 모델의 문장 습관이 담긴 대본이라, 종료 판단 실패를 더 현실적으로 재현합니다. 이 방식은 비용도 거의 들지 않습니다.

## 05.9 실제 호출로 확인하려면

실제 모델로 돌려 보려면 호출 대상을 바꾸기만 하면 됩니다. `transport.HttpTransport`가 같은 인터페이스를 갖고 있으므로, 루프 코드는 그대로 둡니다. 이 블록이 하는 일은 환경변수에서 키를 읽어 실제 API를 부르는 전환입니다.

```python
from transport import HttpTransport

result = loop.run(HttpTransport(), "주문 A-1042가 아직 안 왔어요. 환불해 주세요.")
print(result["steps"], result["log"])
print(result["text"])
```

여기서 확인할 것: `HttpTransport`는 `ANTHROPIC_API_KEY`를 읽습니다. 키가 없으면 시작 단계에서 오류가 나고, 있으면 호출마다 요금이 나갑니다.

이 호출은 유료입니다. 3장의 가격표로 예상 비용을 먼저 계산하십시오. 문의 하나에 3~5회 호출이 일어나므로, 한 번의 실습에 수십 원에서 수백 원이 듭니다. 대본으로 충분히 확인한 뒤에 마지막 한 번만 실제로 부르는 편이 좋습니다.

실제 호출에서 대본과 달라지는 점이 몇 가지 있습니다. 모델이 도구를 부르지 않고 바로 답할 수 있고, 도구를 두 개 동시에 부를 수 있고, 인자를 다르게 넣을 수 있습니다. 이것이 정상입니다. 루프가 그 변수를 견디는지 보는 것이 이 실습의 목적입니다.

호출 뒤에 확인할 것은 세 가지입니다. 단계 수가 몇이었는지, 도구가 몇 번 실행되었는지, 최종 답변이 문의에 답하고 있는지. 단계 수가 상한에 가깝다면 도구 설명이나 system 프롬프트를 고칠 신호입니다.

## 05.10 대본을 테스트로 남기기

대본은 한 번 쓰고 버리는 것이 아닙니다. 코드를 고칠 때마다 다시 돌리는 테스트로 남겨 두면, 나중에 다른 사람이 루프를 건드려도 같은 실패가 돌아오지 않습니다.

이 장의 `verify.py`가 그 역할을 합니다. 루프를 고칠 때마다 돌리고, 여섯 개 중 하나라도 실패하면 그 자리에서 멈춥니다. 특히 3번(잘림)과 4번(없는 도구)은 코드를 정리하다가 조용히 사라지기 쉬운 방어입니다.

테스트를 남길 때 주의할 점이 하나 있습니다. 대본은 모델의 응답을 고정하므로, 모델이 바뀌어도 테스트는 통과합니다. 이것은 장점이자 한계입니다. 루프의 로직을 지키는 데는 충분하지만, 모델의 품질 변화는 감지하지 못합니다. 그 부분은 33장의 평가가 맡습니다.

대본을 늘리는 기준은 "실제로 한 번 겪은 실패"입니다. 상상해서 만든 열 가지보다, 운영에서 한 번 틀어진 상황 하나가 더 값집니다. 오류 로그를 보고 그 응답을 대본으로 옮기십시오. 그 한 건이 다음 번 같은 장애를 막아 줍니다.

대본도 코드와 함께 버전 관리하십시오. 대본이 코드 밖에 있으면 누가 언제 바꿨는지 알 수 없고, 테스트가 갑자기 통과하는 이유를 찾기 어려워집니다. 함께 두면 변경 이력이 같은 곳에 남습니다.

## 05.11 워크스페이스 예제 안내

예제 폴더는 `projects/claude-architect-book/work/ch05-agent-loop/`입니다. 본문에서 쓰는 파일은 여섯 개이고, 각각의 역할은 다음과 같습니다.

| 파일 | 역할 |
|---|---|
| `transport.py` | 모델 호출을 감싼다. 대본 재생과 실제 HTTP 호출 두 가지 |
| `schemas.py` | 도구 정의 3개와 system 프롬프트 |
| `tools.py` | 주문·고객 조회, 상담원 이관의 가짜 구현 |
| `loop_v1.py` | 일부러 틀린 초안 |
| `loop.py` | 고친 루프 |
| `verify.py` | 여섯 시나리오 검증 |

실행은 폴더 안에서 `python3 verify.py`입니다. 대본을 바꾸고 싶으면 `fixtures/happy.json`을 고치면 됩니다. 실제 모델로 돌려 보려면 `transport.HttpTransport`를 쓰고 `ANTHROPIC_API_KEY`를 설정하십시오. 이때는 호출마다 요금이 나갑니다.

여섯 파일이 많아 보이지만, 실제로 읽을 것은 `loop.py`와 `verify.py` 둘입니다. 나머지는 그 둘을 돕는 준비물입니다. 폴더에는 `sdk_check.py`도 있는데, 4장의 SDK 호출 경로를 따로 확인하는 보조 스크립트입니다.

## 05.12 이 루프를 그대로 쓰면 안 되는 순간

이 장의 루프는 읽기 도구만 다룹니다. 실제 업무에는 상태를 바꾸는 도구가 있습니다. 환불 처리, 주문 취소, 메시지 발송이 그렇습니다. 이런 도구를 같은 방식으로 붙이면 사고가 납니다.

가장 위험한 것은 반복입니다. 쓰기 도구는 두 번 실행하면 두 번 환불됩니다. 이 장의 중복 감지는 같은 인자면 막아 주지만, 인자가 조금 달라지면 통과합니다. 쓰기 도구에는 별도의 확인이 필요합니다. 사용자의 명시적 요청이 있었는지, 금액이 상한 안인지, 이미 처리되지 않았는지를 코드로 확인하는 단계입니다.

두 번째는 승인입니다. 환불 금액이 일정액을 넘으면 사람의 승인이 필요합니다. 이 승인을 모델의 판단에 맡기면 안 됩니다. 9장에서 프로그램적 게이트와 프롬프트 지시를 나눠 다루는 이유가 여기 있습니다.

세 번째는 병렬 실행입니다. 모델이 쓰기 도구 두 개를 한 응답에서 부를 수 있습니다. 순서가 중요하다면 병렬을 꺼야 하고, 이 장의 코드는 그 설정을 갖고 있지 않습니다. 14장에서 이 조절을 다룹니다.

이 세 가지를 한 문장으로 줄이면 이렇습니다. 읽기는 루프가 감당하지만, 쓰기는 사람의 의도를 확인한 뒤에 해야 합니다. 이 원칙은 7부의 프로젝트까지 그대로 이어집니다. 루프가 똑똑해질수록 확인의 자리도 함께 늘려야 합니다.

## 05.13 다음 장이 왜 필요한가

이 장의 루프는 돌아가지만, 여전히 부족한 점이 있습니다. 종료 판단은 있지만 **재개**가 없고, 대화가 길어지면 이력이 무한정 커지고, 여러 에이전트가 협업하는 구조가 없습니다. 6장에서 이 루프의 수명주기를 다듬고, 11장에서 세션과 재개를 붙입니다.

더 근본적인 부족함도 있습니다. 이 루프는 한 번에 한 문의만 처리하고, 진행이 없다고 판단하면 포기합니다. 운영에서는 포기 전에 사람에게 넘기는 편이 대개 낫습니다. 그 설계를 28장에서 다룹니다.

## 05.14 이 장의 체크리스트

- [ ] 루프의 종료 근거가 `stop_reason`임을 설명할 수 있다.
- [ ] 텍스트 유무로 종료를 판단하면 왜 실패하는지 안다.
- [ ] `max_tokens` 잘림을 정상 응답으로 쓰지 않는다.
- [ ] 모르는 `stop_reason` 값을 예외로 처리했다.
- [ ] 도구 실행 실패를 `tool_result`로 돌려준다.
- [ ] 없는 도구 이름을 만나도 루프가 죽지 않는다.
- [ ] 같은 호출 반복을 감지하고 모델에게 알린다.
- [ ] 단계 상한을 두었고, 상한에 닿으면 예외로 알린다.
- [ ] `verify.py`의 여섯 시나리오를 직접 돌려 봤다.
- [ ] 검증하지 못한 부분(모델의 도구 선택)을 안다.
